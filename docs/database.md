# Database model

One SQL Server database with a shared schema. Tenants are isolated by an EF Core global query filter on `TenantId` plus write-time checks in `SaveChanges`. This document describes the stored model; planned work is in the [roadmap](roadmap.md).

## Structure

```text
Tenant (a company using the platform: the isolation boundary)
  ├── OrganizationUnit "Company" (the business root, exactly one, always Active)
  │     └── OrganizationUnit (Region, Branch, Team, Grouping; one parent each; Active, Inactive or Archived)
  ├── TenantRole → TenantRolePermission (a state entity: Create, Active, Deleted)
  ├── TenantSetting (one value per setting key; pinned at startup and onboarding)
  ├── Qualification (the catalogue: a state entity, Create, Active, Archived) ← ResourceQualification → Resource (a staff member)
  ├── Service (the service catalogue: Create, Active, Archived) → ServiceQualification (link rows, each Required or Preferred) → Qualification
  ├── WorkPattern → WorkPatternSegment (Draft, Published, Archived, Deleted; segments owned, deleted with a draft)
  ├── ResourcePatternAssignment (a pattern given to a staff member: Registration, Active, Inactive, Deleted)
  ├── ResourceAbsence (a staff member's planned leave or sick leave: Requested, Approved, Rejected, Canceled; commented)
  ├── ClosedDay (a day or period nobody works, for the whole organization or one unit and the units below it; no lifecycle)
  ├── Customer (Create, Active, Inactive, Deleted) → CustomerContact (Create, Active, Inactive, Deleted; deleted with its customer)
  ├── Job (Create, Registration, AwaitingCoordination, Coordinating, Confirmed, InProgress, Completed, CanceledByCustomer, CanceledBySupplier, Deleted; for a customer, its contact and a unit) → JobTimeSlot (owned weekly times) and JobSlot (Create, Active, Canceled, Deleted) → JobSlotQualification (link rows), RequestRound (Create, Open, Filled, Closed) and SlotAssignment (a staff member asked or assigned: Create, Requested, Accepted, Declined, Assigned, NotSelected, Canceled; commented; optionally tied to a request round) → Resource
  ├── Supplier (a customer portal's staffing company: Create, Active, Inactive) ← Order (a portal's order for a job: Create, Registration, Sent; linked to the staffing company's Job by cross-tenant ids, never a foreign key) → OrderLine (owned rows: a service and how many people) → OfferedService (the portal's read-only copy of a service its supplier offers)
  ├── OutgoingMessage (a step's notice, written with it) → StoredMessage (its in-app delivery) → MessageRecipient (one per person, read flag)
  └── ApplicationUser → OrganizationUnitUserRole (role held on a unit, granted tenant-wide)
```

One tree of organization units per tenant ([ADR 0021](adr/0021-one-organization-tree-per-tenant.md)): its root is the `Company` unit, the business itself, and every other unit sits below exactly one parent.

## Base types

Conventions for every entity follow [ADR 0022](adr/0022-data-model-conventions.md) and are enforced by model tests.

- **`ITenantEntity`**: `TenantId` (`Guid`), `Created`, `CreatedById`, `Modified`, `ModifiedById`, `ImpersonatedById`. Every type implementing it gets the tenant query filter. `Modified`/`ModifiedById` record the last writer of a row and stay null until the first update; `SaveChanges` stamps all of them (see [Tenant isolation](tenant-isolation.md), "Stamping").
- **`TenantEntityBase`** implements `ITenantEntity` and adds `Id` (`Guid`, generated by EF, never assigned by hand). Every tenant row's configuration calls one shared method, `ConfigureTenantEntity()` (`Staffora.Data/Configurations/TenantEntityConfiguration.cs`, constrained to `ITenantEntity`), that marks the tenant and creation columns required, makes `TenantId` read-only after save, and adds a `TenantId` index and `CreatedBy`, `ModifiedBy` and `ImpersonatedBy` foreign keys to `AspNetUsers` with `NoAction`. The key `Id` comes from EF's convention.
- **Model conventions** (ADR 0022): `DateTime` reads back as UTC (`ApplicationDbContext.ConfigureConventions` applies `UtcDateTimeConverter` to every `DateTime` and `DateTime?`), persisted enums declare explicit values and are never renumbered, every string has a maximum length, every relationship is `NoAction` unless the child is an owned row without a lifecycle, and `Guid` keys are generated by EF.

  The model tests in `Staffora.Test/Unit/Data/ModelConventionTests.cs` enforce each rule over the whole model; their two allow-lists (owned rows that cascade, and ASP.NET Identity's own unbounded columns such as `PasswordHash`) are the only exceptions.
- **State entities** have a lifecycle: `TenantStateEntityBase<TState>` for tenant-owned ones and the tenant-free `StateEntityBase<TState>` for `Tenant`, both with a `Guid Id`, `State` and `IsInTransition`. Those two are the only concurrency tokens, configured for every state entity by `ConfigureStateEntities()` (`Staffora.Data/Configurations/StateEntityConfiguration.cs`, no attributes on the entities): an update over a row whose state moved, or that a transition has locked, is refused. How states, transitions and field access work is in the `workflow-state-entities` skill (`.claude/skills/workflow-state-entities/SKILL.md`).

**Transitions.** Transitions run only through `WorkflowService` (`Staffora.Services/Workflow/WorkflowService.cs`, the lock statement in `WorkflowService.Locks.cs`, ADR 0002). In one transaction it:

1. takes the application locks registered for the entity type (`TenantStepLock<TEntity>`, [Application locks](#application-locks)) first, before anything of the step is read;
2. locks the entity and every other lock candidate with one `ExecuteUpdate` per entity type, refusing the transition when another one holds a candidate;
3. asks the registered delete blockers about every entity it would delete (an `IDeleteBlocker` vetoes with its reason);
4. executes the engine and records the state history;
5. removes every entity the transition left in a delete state, after its registered delete cleanups ran (ADR 0016);
6. writes queued messages as outbox rows linked to the history ([OutgoingMessage](#outgoingmessage)) and saves inside a transition save scope.

The messages go to the `IOutgoingMessageDispatcher`, and `AfterCommit` work runs, only after the commit.

**Field access in `SaveChanges`** (`Staffora.Data/ApplicationDbContext.WorkflowFieldEnforcement.cs`). Refused with a `WorkflowFieldEditException`:

- an update that changes `State` or `IsInTransition` outside a transition save scope (`BeginTransitionSaveScope`: a source scan lets only allow-listed files name it, in production only `WorkflowService` around a transition's save, always as the resource of a `using`);
- an update of a field the **persisted** state does not make editable;
- outside a transition save scope, an update or delete of a row whose **stored** `IsInTransition` is true (a transition holds it), in system scope as well;
- any delete of a state entity outside a transition save scope, in system scope as well: it leaves only through its delete transition, so a row removed in one save can never come back with the same key in another state in the next;
- outside system scope and outside a transition save scope, an insert in a state that is not an entry state (`[EntryState]`, or a member named `Create`), so no row starts in a state no transition led to;
- outside a transition save scope, an insert already held (`IsInTransition` true), in system scope as well, as no transition would release it.

Only properties that are marked modified and differ from the stored row count, so an unchanged locked field passes. The key, `TenantId` and the audit columns are not workflow fields, and the tenant checks run first.

**Declared child collections.** A child row in a collection its parent's workflow **declares** (names by `.Field(e => e.Lines, …)` or an area in at least one state) is judged against the parent's stored state however it is written: a tracked edit, an updater over the child itself, or the parent's `DetachedEntityUpdater<T>`, which refuses a locked collection itself first. Its insert, update or delete is refused while the parent's state does not make the collection editable or a transition holds the parent, and a moved child is judged against both parents.

A child is not judged:

- while it or its parent is in a transition save scope;
- when its update changes no value (as `Update()` on a whole detached graph marks it);
- through a parent inserted or deleted in the same save;
- by the stored state of a parent updated in the same save (that parent's original state is used, which its concurrency tokens guard).

A collection that only follows its parent's state default is not judged, so a tenant's roles and units stay writable under the tenant's read-only default. `ExecuteDelete` of a state entity and every bulk statement on `StateHistoryEntry` are refused in every scope (see "Bypass rules" in [Tenant isolation](tenant-isolation.md)).

## Tenant isolation

Every `ITenantEntity` carries a query filter on `TenantId` that fails closed: with no runtime tenant it passes no row. `SaveChanges` checks every write against the runtime tenant and the stored row, stamps the audit columns, and enforces the listed exceptions (`Tenants`, attribute definitions and values, `ErrorLogs`, `ImpersonationAudits`). Crossing the boundary takes a logged system-scope lease on the context. The rules, the exceptions to the filter, stamping, bulk statements and the allow-lists are described in [Tenant isolation](tenant-isolation.md).

## Application locks

Steps that judge a rule over several rows of a tenant run one at a time per tenant and area, under an exclusive SQL Server application lock (`sp_getapplock`). Every application lock is declared and taken in one place, `AppLock` (`Staffora.Data/AppLock.cs`):

| Lock | Rank | Resource | Taken by |
|---|---|---|---|
| `AppLock.Structure` | 1 | `org-structure:<tenant>` | structure writes: unit, role and user steps, role holdings, `CompanyRoot.EnsureAsync`, resource steps and job steps ([OrganizationUnit](#organizationunit)) |
| `AppLock.Schedules` | 2 | `schedules:<tenant>` | work pattern and pattern assignment steps |
| `AppLock.Customers` | 3 | `customers:<tenant>` | customer, contact, service and job steps |
| `AppLock.Jobs` | 4 | `jobs:<tenant>` | job, slot, assignment, request round, qualification, service and absence steps |
| `AppLock.CommentThread` | 5 | `comment-threads:<tenant>:<record>` | every writer of a record's comment thread (10 seconds) |
| `AppLock.TenantCreate` | 0 | `tenants:create` | the platform console's tenant creation (platform level) |
| `AppLock.PlatformBootstrap` | 0 | `Staffora.PlatformBootstrap` | the platform bootstrap, owned by the session (60 seconds) |

- **Owned by the transaction.** A tenant lock is owned by the caller's transaction and refuses to be taken without one. It is waited for up to 15 seconds unless the table says otherwise. A lock not granted in time throws `AppLockBusyException`, whose `Lock` names the lock and whose message is the lock's `BusyReason`; the structure lock answers with an `OrganizationStructureException` carrying the same reason.
- **Lock order.** Every transaction holds the tenant's row (shared) first, then takes the application locks in rank order, then reads and writes rows. `AppLock.TakeInOrderAsync` takes several locks in that order, so a console step, a tenant's session, a job clock step and a step that moves the tenant never deadlock. Locks of rank 0 are platform-level and name no tenant.
- **Workflow steps.** An entity type's step lock is one generic `TenantStepLock<TEntity>` (`Staffora.Services/Workflow/TenantStepLock.cs`), registered per entity with `services.AddStepLock<TEntity>(...)` in `WorkflowServiceRegistration`. `WorkflowService` opens the step's transaction and takes the registered locks before anything of the step is read.
- **Mapping.** `Job` takes Structure, Customers and Jobs. `Service` takes Customers and Jobs. `OrganizationUnit`, `ApplicationUser`, `TenantRole` and `Resource` take Structure. `WorkPattern` and `ResourcePatternAssignment` take Schedules. `Customer` and `CustomerContact` take Customers. `JobSlot`, `SlotAssignment`, `Qualification`, `RequestRound` and `ResourceAbsence` take Jobs. Tenant creation uses `TenantCreateStepLock` over `AppLock.TenantCreate`.

## Isolation level

The database runs with `READ_COMMITTED_SNAPSHOT` on: a plain read sees committed row versions and never waits on another transaction's uncommitted rows ([ADR 0046](adr/0046-the-database-reads-committed-rows-by-row-versioning.md)). `ApplicationDatabase.MigrateAsync` (`Staffora.Data/ApplicationDatabase.cs`) turns it on once, right after the migrations; the app at startup, the end-to-end preparation and the integration test pool all migrate through it.

- Tenant reads cannot seek on the query filter's predicate, so they scan the clustered index, where the rows of every tenant are mixed. Under locking read committed such a scan inside a write transaction could wait on another tenant's freshly inserted row and deadlock with it. Row versioning removes that wait.
- Reads that judge a rule stay locking through their hints: the structure check reads `WITH (READCOMMITTEDLOCK, FORCESEEK)`, seeking the tenant's own index range so it never locks another tenant's rows, and the tenant's row is held with `HOLDLOCK`.
- Snapshot isolation (`ALLOW_SNAPSHOT_ISOLATION`) stays off. Structure writes open their transaction at read committed by name (`OrganizationStructureIsolationLevel`).

Verified by: `TenantLockOrderTests` (two unrelated tenants creating units and sending orders at once never deadlock).

## Entities

### Tenant

The isolation boundary. A state entity: `Tenant : StateEntityBase<TenantState>`.

- `Name` (max 200, unique: `IX_Tenants_Name`, compared as the database's collation compares, so case and trailing spaces aside; the tenant service trims it and refuses a taken one first), `Description` (max 500), `Created`, `CreatedById`, `IsRootTenant` (the platform tenant; a unique index filtered to it holds at most one)
- `State` (`TenantState`: Setup, Active, Suspended, PendingDeletion, Archived) and `IsInTransition` (concurrency tokens). `State` alone says whether a tenant is in use; there is no separate active flag.
- `ParentTenantId` (`Guid?`, [ADR 0007](adr/0007-cross-tenant-ordering-customer-portal.md)) → Tenant, self-reference, NoAction, indexed: the staffing company that manages this tenant, set for a managed customer tenant (the portal's onboarding writes it as it creates one) and null for every other. Never the tenant itself (`CK_Tenants_ParentTenantId_NotSelf`); one level only; written as the tenant is created and never changed afterwards.

  The data context holds it in every scope, a step's own save scope included (`ApplicationDbContext.TenantIsolation.cs`, `CheckStaffingCompaniesAsync`): a tenant is created naming a stored tenant that is neither the platform tenant nor managed itself, the platform tenant names none, and a later save that changes it, or clears it, is refused with a `TenantIsolationException`; `BulkUpdateGuard` refuses an `ExecuteUpdate` that sets it.

  It opens no read path: it only says which two tenants may exchange integration messages (`TenantStates.AreLinked`).
- Navigation collections: `TenantRoles`, `OrganizationUnits` (its one organization tree, the `Company` root among them)

`Tenant` is tenant-free: one `Guid Id` and no `TenantId`. Its own query filter shows a context only its runtime tenant's row, and it is written only in system scope (see [Tenant isolation](tenant-isolation.md)).

Its workflow (`TenantWorkflowAttribute`) follows the lifecycle in [PRODUCT.md](../PRODUCT.md): a tenant starts in Setup (the entry state), is activated, can be suspended and reactivated, is scheduled for deletion from Active or Suspended (and taken off the schedule back to Suspended), and is archived from Pending deletion, by a platform owner or, once the grace period after its deletion was scheduled is over, by the retention pass's system step `tenant-purged`, which removes all its data first ([Retention](features/operations.md#retention)).

Every other transition is marked `RequiresPlatformOwner`, and the platform tenant (`IsRootTenant`) is never suspended or scheduled for deletion, and its name and description are fixed (its Active save is refused, and `TenantService` refuses any edit of it). Setup and Active both require `Name` and leave `Description` optional, and each has a Save step (an active company can be renamed); the other states are read-only.

A tenant created from the platform console gets its system account, its Company root and its pinned time zone (`General.TimeZone`, the platform's zone as configured then, stamped with the system account) in the create's own transaction (`TenantService.CreateTenantAsync`).

A customer portal's tenant is created otherwise: inside its staffing company's "Enable portal" step on the customer, straight into Active, in system scope, naming the staffing company as `ParentTenantId`, created by its own system account, and given the same rows in the same transaction (`TenantOnboardingService.OnboardManagedTenantAsync`); its history starts with the Activate entry, recorded on its behalf, its own system account the actor (`StateHistoryWriter.AddOnBehalfOf`), and its Company root takes the customer's own name, never the tenant row's numbered one.

Its edition (a customer portal) is derived from `ParentTenantId`, never stored (`TenantEditions.Of`, [Authorization](authorization.md#the-edition-ceiling)).

### OrganizationUnit

One node in the tenant's single organization tree ([ADR 0021](adr/0021-one-organization-tree-per-tenant.md)). A state entity: `TenantStateEntityBase<OrganizationUnitState>`, decorated with `[OrganizationUnitWorkflow]`.

- `Name` (max 200, `OrganizationUnit.NameMaxLength`), `Description` (max 500, `DescriptionMaxLength`), `UnitType` (`OrganizationUnitType`: Company 0, Region 1, Branch 2, Team 3, Grouping 4)
- `State` (`OrganizationUnitState`: Create 0, Active 1, Inactive 2, Archived 3, Deleted 4) and `IsInTransition`, the concurrency tokens of every state entity. Only an Active unit is in use: it takes new role holdings and its holdings grant (the Company root always counts as in use; a holding on a unit out of use grants nothing, see [Authorization](authorization.md#role-holdings-and-inactive-units)).

  The entry state is 0, so a unit written without naming a state fails closed; every path that writes a unit in use names Active itself (the Company root's ensure, the seeding, the end-to-end fixture, the workflow's create step).
- **Lifecycle** (`OrganizationUnitWorkflowAttribute`): Create → Active (create, below a unit in use); Active ⇄ Inactive (deactivate, which takes every active unit below out of use with it, each through its own step with its own history; reactivate, only below a unit in use); Active or Inactive → Archived (only once every unit below is archived), Archived → Inactive (restore, only below a unit that is not archived); Active, Inactive or Archived → Deleted (only with no unit below it and no registered delete blocker reporting use; the role holdings on it are such a use, `RoleHoldingsBlockUnitDelete`).

  The root never leaves Active. Active is the state's save, its fields editable (the name required); an inactive or archived unit is read-only. Every step runs under the tenant's structure lock, and the deactivate, reactivate, archive (of an active unit; an inactive unit's holdings grant nothing already) and delete steps keep to the grant ceiling ([Authorization](authorization.md), "Grant ceiling").
- `TenantId` → Tenant (`Tenant.OrganizationUnits`), NoAction
- `ParentId` (`Guid?`) → OrganizationUnit (`Parent`, `Children`), self-reference, NoAction. Null only for the `Company` root.
- Exactly one `Company` root per tenant, without a parent, always active and never deactivated, deleted or archived; one parent per unit, in the same tenant; no cycles; names unique among siblings; a `Grouping` holds no roles or members. The root is named after the tenant when it is created; after that it is a unit like any other in this respect, renamed in its own dialog, and renaming the tenant does not rename it (nor the other way round).
- The platform tenant's tree is its root alone: no other unit and no role holding is written there (the platform owner holds the `Admin` role, not tenant roles; [ADR 0012](adr/0012-platform-owner-and-tenant-onboarding.md)).
- `Attributes`: custom field values (see [Entity attributes](#entity-attributes))

**The structure policy.** `OrganizationStructurePolicy` (`Staffora.Core/Entities/Organization/`) states these rules once, in the domain and without data access, so the services and the data layer share it.

A caller loads the tenant's units into an `OrganizationStructure` (ids, names, types and one parent link each), applies the change it proposes (`WithUnit`, `Moved`, `Edited`) and asks `FirstNewViolation(before, after)`, which returns the reason of the first rule the change breaks that the stored tree did not already break, so a tree written wrong past the services can be put right step by step but never made worse.

A rule is compared by the unit and the rule's kind (`OrganizationStructureViolation.Kind`), not by its reason's text, which names the unit, so renaming a unit in or below a stored cycle is no new break.

A unit in a cycle is refused with `CycleReason`, one below a cycle with `CutOffReason`; every walk remembers the units it passed, so a stored cycle ends it. "One parent" is not a check: a unit stores one `ParentId` and a structure unit holds one link, so a second parent cannot be stated, and a move replaces the link (`OrganizationUnitModelTests` proves the schema side).

`CheckRoleHolding` refuses a role on a grouping, and, given the structure, on a unit whose parents do not lead to the root (in or below a stored cycle, `CutOffHoldsNoRoles`); `CheckTypeChange` refuses a unit with role holdings turning into one.

Every path that writes units asks it: `OrganizationService.CreateOrganizationUnitAsync` and `UpdateOrganizationUnitAndTransitionAsync` (a changed parent is a move), `RoleHoldingService.AssignUserToRoleAsync`, the Company root's ensure (`Staffora.Data/CompanyRoot.cs`) and the seeding of a head office (`DatabaseSeeder`, the end-to-end fixture). Each refusal is a failed `Result` with the policy's reason.

A parent of another tenant reads as not found through the filter, and the tenant isolation's reference check refuses it past the service. The services also refuse a name, description or custom field text over its column's length with a described reason, and map the sibling-name index's refusal (a name the database's collation takes as a sibling's, such as one in full-width letters) to the policy's sibling-name reason.

**One writer at a time per tree.** Two writes judged at once would each see the tree without the other: crossing moves would store a cycle, and a unit turned into a grouping while a role is given on it would keep the holding.

So each structure write (every step of a unit and of a role through `WorkflowService`, whose `IStepLock` opens the step's transaction and takes the lock before anything of the step is read; `AssignUserToRoleAsync`; `CompanyRoot.EnsureAsync`) opens a transaction at read committed and first takes the tenant's structure lock, `ApplicationDbContext.LockOrganizationStructureAsync` (`AppLock.Structure`: resource `org-structure:<tenant>`, owned by the transaction, waited for up to `AppLock.Structure.TimeoutMilliseconds` and otherwise refused with `AppLock.Structure.BusyReason`; [Application locks](#application-locks)).

The isolation level is named (`OrganizationStructureIsolationLevel`) because a pooled connection keeps the isolation level its previous user set, snapshot for one. No production path opens a transaction at another level and the database does not allow snapshot isolation ([Isolation level](#isolation-level)), so this guards a future caller that would; the integration tests that run snapshot transactions do so in an isolated database and pool of their own (`Staffora.Test/Integration/README.md`).

It then reads the tree, judges and saves under the lock, so the next writer is judged on the tree this one left.

Below the services the data context fails closed on its own (`ApplicationDbContext.OrganizationStructure.cs`): a save that inserts or deletes a unit, changes a unit's `ParentId`, `UnitType` or `State`, or inserts a holding or moves one to another unit takes the same lock in its transaction (its caller's, behind a savepoint, or one it opens at read committed).

Before it writes, a deleted unit stored as the Company root refuses it with `RootIsNeverDeleted` (read from the stored row, so a stub naming another type does not pass), and so does a deleted unit that a unit staying in the tree sits below, with `UnitsBelowReason`.

After it writes and before it commits it checks each tenant it wrote. One recursive query finds the units that no longer reach a root through their parents. The save is refused for:

- a unit it wrote among them (`CutOffReason`), or a holding it wrote on one (`CutOffHoldsNoRoles`);
- a holding it wrote on a grouping, or a unit it wrote that is a grouping with holdings (the grouping reasons);
- a holding it wrote (inserted, or moved to another unit) on a unit out of use, any but the Company root (`OutOfUseHoldsNoRoles`);
- in the platform tenant, any unit other than the root and any holding (`PlatformTreeIsRootOnlyReason`);
- for every unit it wrote, the rules of use: the root in any state but Active (`RootStaysActive`), a unit in use below a unit that is not (`InUseBelowOutOfUseReason`) or a unit out of use above one in use (`OutOfUseAboveInUseReason`), a unit not archived below an archived one (`BelowArchivedReason`) or an archived one above a unit that is not (`ArchivedAboveUnarchivedReason`).

The check's queries read every table `WITH (READCOMMITTEDLOCK, FORCESEEK)`, seeking the tenant's own index range: they see the committed rows and the save's own, under any isolation level, where a snapshot transaction would otherwise judge the tree as it was when its snapshot began, without a move committed since under the same lock. A refusal rolls the save back and throws an `OrganizationStructureException` carrying the reason, which the services return as their `Result`.

Any other failure between the savepoint and the end of the check (a cancelled or failed check query, a row the database refused) also rolls a caller's transaction back to the savepoint, never cancelled, before it is rethrown, so a caller that catches it and commits keeps nothing the check did not pass; a transaction the save opened rolls back as it is disposed.

Only what the save wrote is judged, so a tree stored wrong before these checks can still be repaired. The lock is taken only once the tenant's row is held (shared), in every scope, the platform console's steps and the ensures included, so every transaction locks a tenant's row, then the lock, then rows ([Application locks](#application-locks)).

`BulkUpdateGuard` refuses an `ExecuteUpdate` of a unit's `ParentId`, `UnitType` or `State` or a holding's `OrganizationUnitId`, and any `ExecuteDelete` of units, which would skip the check.

**The Company root.** Every path that creates a tenant gives it its root through `CompanyRoot` (`Staffora.Data/CompanyRoot.cs`): `EnsureAsync(context, tenantId)` adds the root, named after the tenant (a customer portal's after its customer: the tenant row may carry a number the portal's people must not read) and stamped with the tenant's system account (ensured first), inside a system-scope lease of its own and under the tenant's structure lock, and finds an existing one instead of adding a second, also when several starts ensure it at once. The Development seeder (the platform tenant), the platform bootstrap (the platform tenant), the test scenarios and the end-to-end fixture call it.

`TenantService.CreateTenantAsync`, the tenant dialog's create, calls `EnsureAsync` on the create step's own context, after the new tenant's system account and inside the step's transaction (`WorkflowService.CreateAndTransitionAsync`'s `afterInsert`), so a refused create leaves no root; tenant onboarding builds on that create.

**Guards in the database.** A write past the services fails closed on the rules the database can check cheaply: a unique index filtered to `UnitType = 0` (`IX_OrganizationUnits_TenantId_OneCompanyRoot`) allows one Company unit per tenant; the check `CK_OrganizationUnits_ParentUnlessCompany` requires a parent exactly when the unit is not the Company; `CK_OrganizationUnits_NotOwnParent` keeps a unit from being its own parent; and the unique index on `(TenantId, ParentId, Name)` (`IX_OrganizationUnits_TenantId_ParentId_Name`, `OrganizationUnitConfiguration.SiblingNameIndex`) keeps sibling names apart.

A longer cycle and a holding on a grouping are refused by the data context's structure check above.

A unit is deleted only through its workflow's delete step (`SaveChanges` refuses any other delete of a state entity, and a bulk delete of units altogether): the step refuses the root and a unit with units below it with their reasons, and the registered delete blockers a unit in use (its role holdings), each inside the step's transaction; the data context's check before the save refuses the root and a unit with units below it again, and the `NoAction` foreign keys stay the last line.

### OrganizationUnitUserRole

Holds a tenant role for a user on one organization unit. `TenantEntityBase`.

- `UserId` → ApplicationUser, `TenantRoleId` → TenantRole, `OrganizationUnitId` → OrganizationUnit (required; the root means the whole company); all NoAction
- Unique `(TenantId, UserId, TenantRoleId, OrganizationUnitId)`
- The role's permissions apply tenant-wide; the unit records where the person works and, for the Staff role, which units the staff member belongs to.
- `RoleHoldingService.AssignUserToRoleAsync(userId, organizationUnitId, tenantRoleId, tenantId)` checks, under the tenant's structure lock, that the tenant is not the platform tenant, that the holder is an active person of the tenant, that the unit and the role are the tenant's own (read through the filter) and the role active, that the unit is no grouping, is in use (Active, or the root) and reaches the root through its parents (not in or below a stored cycle), and that the user does not hold the role on that unit already, each with its reason.

  A holding on a unit that is later deactivated or archived stays stored and grants nothing until the unit is active again ([Authorization](authorization.md#role-holdings-and-inactive-units)). A holding keeps its unit and its role from being deleted: the delete blockers `RoleHoldingsBlockUnitDelete` and `RoleHoldersBlockRoleDelete` refuse them with the number of holdings.

  Giving or taking away a holding brings the holder's staff record along in the same transaction (`ResourceLinker`, see [Resource](#resource)).

### Resource

A staff member (the UI's word; [ADR 0008](adr/0008-users-become-resources-through-a-role.md)): the staffable side of one user. A state entity: `TenantStateEntityBase<ResourceState>`, decorated with `[ResourceWorkflow]`. Its qualifications ([ResourceQualification](#resourcequalification)), schedules, absence and assignments attach to it, never to the user.

- `UserId` → ApplicationUser (NoAction; a user is never deleted), unique (`IX_Resources_UserId`): one record per user, whoever writes it, so a second one is refused by the database even past the linker; never changed once saved.
- `State` (`ResourceState`: Registration 0, Active 1, Inactive 2) and `IsInTransition`. Only an Active record of an active user is in service and staffable (`StaffServiceRules.InService`, which the staffing dialog's candidates and the availability read). The entry state is 0, so a record written without naming a state is not staffable.
- **Lifecycle** (`ResourceWorkflowAttribute`), every step system-driven (no button), each naming `ResourcesManage`: Registration → Active (activate), Active → Inactive (deactivate), Inactive → Active (reactivate), Registration → Inactive (withdraw). No delete state: a record keeps its history. Every step runs under the tenant's structure lock.

  The public paths of `WorkflowService` (a step by key or by target state, a create, a dialog's edits) refuse a system-driven step whoever asks (`WorkflowService.SystemDrivenRefusal`), the tenant's system owner and a holder of `ResourcesManage` included, so nobody moves a record past the rule below (`SystemStepTests`).
- **Written only by `ResourceLinker`** (`Staffora.Services/Resources/`; `StaffRecordScanTests` for its writes, the public paths' refusal above for its steps), in the transaction of the write that calls for it, under the tenant's structure lock that write holds: a role given or taken away (`RoleHoldingService.AssignUserToRoleAsync`, `RemoveUserFromRoleAsync`), and the follow-ups of a user step that changes the user's state, of a role step (the staff flag) and of a unit step that takes units out of use or puts them back, every unit the step cascades to included (`IStepFollowUp`: `UserStepsKeepStaffMembers`, `RoleStepsKeepStaffMembers`, `UnitStepsKeepStaffMembers`).

  The rule (`ResourceLinker.TargetState`): a user holding a role whose holders are staff members (`TenantRole.ApplyResourceMembershipToUser`, an active role) on a unit in use has a record, created in Registration and Active while the user is active (Registration until first active, Inactive once deactivated); holding none any more makes it Inactive.

  Each move is the resource workflow's step, run inside the caller's transaction (`WorkflowService.RunSystemStepInTransactionAsync`) with its history, the user who made the change as the actor; a refused or failed move rolls the caller's write back.
- `Memberships`: `ResourceUnitMembership` rows, no field of the workflow (derived rows the linker writes).

### WorkPattern

The hours a staff member works: a cycle of whole weeks that repeats, each day of it with the segments worked on it. `TenantStateEntityBase<WorkPatternState>`, decorated with `[WorkPatternWorkflow]`.

- `Name` (max 100, required), `Description` (max 500), `CycleWeeks` (1 to `WorkPatternRules.MaxCycleWeeks`, 8; check constraint `CK_WorkPatterns_CycleWeeks`). Day 0 of the cycle is the Monday of its first week.
- `State` (`WorkPatternState`: Draft 0, Published 1, Archived 2, Deleted 3) and `IsInTransition`. Only a Published pattern is given to staff members ([ResourcePatternAssignment](#resourcepatternassignment)); the entry state is the Draft, assigned to nobody.

  Archiving a pattern staff members have is allowed: their assignments keep it as it is (a published pattern never changes, so their hours never move), and an archived pattern is given to nobody new.

  Every step takes the tenant's schedule lock, which puts the pattern's steps in one order with the assignments' steps, and a pattern an assignment names is not deleted (`PatternAssignmentsBlockPatternDelete`, a delete blocker; only a draft is deleted and no draft is given, so it answers only for a row written past the workflow).
- **Lifecycle** (`WorkPatternWorkflowAttribute`), every step needing `ManageWorkPatterns`: Draft's save (the state's save step; in the dialog's create mode the step that creates the draft), Draft → Published (publish, confirmed), Published → Archived (archive, confirmed), Draft → Deleted (delete, confirmed; the segments go with it, the history stays).

  A Published or Archived pattern changes no more and is never deleted; a changed version is a new draft copied from it ("Copy to new draft", `WorkPatternService.NewWorkPatternAsync` with the pattern to copy, created by the draft's own save). The save and the publish judge the segments (`WorkPatternRules.Problems`: each on a day of the cycle, starting before it ends, none overlapping another of its day), and the publish needs at least one.
- `Segments`: `WorkPatternSegment` rows, a declared collection of the workflow's Segments area (editable only in Draft).

### WorkPatternSegment

One stretch of work on one day of a pattern's cycle. An owned row without a lifecycle (`TenantEntityBase`: a tenant row like every other).

- `WorkPatternId` → WorkPattern (**Cascade**: deleted with a deleted draft, ADR 0016's owned rows), indexed with `DayIndex`.
- `DayIndex` (0 to seven times the cycle's weeks, less one), `Start` and `End` (`TimeOnly`, local times of the tenant's zone, ADR 0020; `time` columns). Check constraints `CK_WorkPatternSegments_DayIndex` (not before day 0) and `CK_WorkPatternSegments_StartBeforeEnd`; the pattern's steps judge the full rules first, and `WorkPatternService` refuses an edit they refuse with each problem in words.
- How a pattern repeats over calendar days from an anchor date is `WorkPatternRules.Expand` (pure; the availability's core builds on it): the anchor is a Monday, day 0 of the cycle (any other is refused), and it answers local dates and times of day only; the availability turns them into instants in the tenant's time zone ([Schedules and availability](features/schedules-and-absence.md#schedules-and-availability)).

### ResourcePatternAssignment

A work pattern given to a staff member: the staff member works by the pattern from a date. `TenantStateEntityBase<ResourcePatternAssignmentState>`, decorated with `[ResourcePatternAssignmentWorkflow]`; shown in its own dialog (`PatternAssignmentDialog`, token `patternassignment`), opened from the user dialog's Schedule view.

- `ResourceId` → Resource (NoAction; a record is never deleted; never changed once saved), `WorkPatternId` → WorkPattern (NoAction), indexed `(ResourceId, State, EffectiveFrom)` for the availability's read of many staff members' active assignments and the step guard's read of one staff member's.
- `EffectiveFrom` and `EffectiveTo` (`DateOnly`, calendar days of the tenant, both included; `EffectiveTo` null applies until further notice; check constraint `CK_ResourcePatternAssignments_EndNotBeforeStart`), `CycleAnchor` (`DateOnly`, a Monday: day 0 of every cycle, so in a cycle of several weeks the first day of its first week; check constraint `CK_ResourcePatternAssignments_AnchorMonday`, counted in days from 1900-01-01, a Monday, so it does not depend on the session's first day of the week). A new assignment starts today on the tenant's wall clock, its cycle on this week's Monday.
- `State` (`ResourcePatternAssignmentState`: Registration 0, Active 1, Inactive 2, Deleted 3) and `IsInTransition`. Only an Active assignment gives hours (the availability reads no other), and **a staff member has at most one active assignment on any date** (`ScheduleRules`). The entry state is 0, so an assignment written without naming a state gives no hours.
- **Lifecycle** (`ResourcePatternAssignmentWorkflowAttribute`), every step needing `AssignWorkPatterns`: Registration's save (the state's save step; in the dialog's create mode the step that creates it), Registration → Active (activate), Registration → Deleted (delete, confirmed; one that never took effect), Active's save (its end date, the state's save step), Active → Inactive (withdraw, confirmed: it gives no hours on any of its dates; its history is kept), Inactive → Active (reactivate). In Registration the pattern, the dates and the anchor are editable; once Active only `EffectiveTo`.
- **Rules**, judged by the workflow's conditions (the dialog in memory, the server inside the step's transaction): the pattern is Published (a draft is given to nobody, an archived pattern to nobody new; the save, Activate and Reactivate ask it, while an active assignment whose pattern was archived later keeps it, saves its end and is withdrawn as any other); the dates are in order and the anchor a Monday (`ScheduleRules.Problems`); the staff member's record is not Inactive; and Activate, Reactivate and the active save share no date with the staff member's other active assignments, read by the step's guard (`PatternAssignmentGuard`, an `IStepPreparation`) and refused with each overlapping assignment named.
- **One writer at a time per tenant.** Every assignment step and every pattern step takes the tenant's schedule lock first (`AppLock.Schedules`, owned by the step's transaction, the tenant's row held before it), so the guard reads the other active assignments on rows no other assignment step changes before the commit (the pattern steps take it only to keep one order with them): of two overlapping activations at once exactly one commits (`PatternAssignmentConcurrencyTests`).

  A lock not granted in time refuses the step with the lock's busy reason (`AppLockBusyException`).
- **The editing model.** A staff member's pattern is replaced by ending the current assignment on a day (its end date) and activating a new one from the day after: neither a gap nor an overlap the user did not choose. Moving an end later into the next assignment is refused; an assignment that was a mistake is withdrawn.
- **A staff member out of service**: the active assignment's save is refused for a staff member whose record is inactive, as the create, Activate and Reactivate are, and the availability gives such a staff member no hours whatever assignments they keep. A create takes the prepared assignment's Save only, and an end before the start is refused with its reason before anything is written.

### ResourceAbsence

A staff member's absence: planned leave, which blocks the staff member once approved, or sick leave, which blocks them from the moment it is reported ([Absence](features/schedules-and-absence.md#absence)).

`TenantStateEntityBase<ResourceAbsenceState>`, decorated with `[ResourceAbsenceWorkflow]`, and a commented record (`ICommentedEntity`: its staff thread holds the questions, the answers and a rejection's reason, read by the staff member and the approvers and written only by the steps' prompts, [ADR 0035](adr/0035-absence-questions-are-workflow-steps.md)); shown in its own dialog (`AbsenceDialog`, token `absence`), opened from the absence page and the user dialog's Absence view.

- `ResourceId` → Resource (NoAction; a record is never deleted; never changed once saved), indexed `(ResourceId, State, FirstDay)` for the availability's read of many staff members' blocking absences and the lists of one staff member's.
- `Kind` (`AbsenceKind`: PlannedLeave 0, SickLeave 1; chosen when reported, never changed afterwards: the save refuses a changed kind; check constraint `CK_ResourceAbsences_KnownKind`, a declared kind only, which the service and the workflow refuse first, `AbsenceRules.IsKnownKind`).
- `FirstDay` and `LastDay` (`DateOnly`, calendar days of the tenant, both included; check constraint `CK_ResourceAbsences_LastNotBeforeFirst`), `StartTime` and `EndTime` (`TimeOnly`, nullable: the time the absence starts on its first day and ends on its last; none is the start and the end of the day; checks `CK_ResourceAbsences_TimesInOrder`, a single day's end after its start, and `CK_ResourceAbsences_EndNotMidnight`). Instants come from them through the tenant's zone (`AbsenceRules.Instants`, ADR 0020).
- `State` (`ResourceAbsenceState`: Requested 0, Approved 1, Rejected 2, Canceled 3, Question 4, StaffQuestion 5) and `IsInTransition`. Question ("Question to the staff member") and StaffQuestion ("Question to the coordinator") are Requested with a person's turn attached (ADR 0035): every reader that counts, lists or blocks requested absences reads them as requested (`AbsenceRules.UndecidedStates`, `ScheduledStates`).

  **Which absence blocks** (`AbsenceRules.Blocks`): Approved of either kind, and an undecided sick leave. The entry state is 0, so an absence written without naming a state is Requested: a planned leave blocks nothing, a sick leave blocks, the safe side for staffing.
- **Lifecycle** (`ResourceAbsenceWorkflowAttribute`):
  - a new absence's first step is Report (`ReportOwnAbsence`, one's own record), Register (`ManageResourceAbsence`, another staff member's) or, for a registration by an approver, Approve for a planned leave or Handled for a sick leave (`ApproveResourceAbsence` and `ManageResourceAbsence`);
  - Requested's save (the state's save step: the period, by the staff member or a holder of `ManageResourceAbsence`, never the kind);
  - Requested → Approved (approve, a planned leave only; handled, `absence-handle-sick`, a sick leave only);
  - Requested → Rejected (reject, with a reason through the comment prompt into the staff thread);
  - Requested, Approved, Question and StaffQuestion → Canceled (cancel, confirmed; the staff member or a holder of `ManageResourceAbsence`).

  An approver never decides their own.

  The questions (ADR 0035): Requested → Question (send a question), Question → Question (send another question; the staff member's save), Question → Requested (the staff member's answer, the words optional; continue without an answer), Requested → StaffQuestion (write a question), StaffQuestion → StaffQuestion (write another question; answer the staff member), StaffQuestion → Requested (mark as handled, `absence-question-handled`); the coordinator's side needs `ApproveResourceAbsence` and never one's own absence, the staff member's `ReportOwnAbsence` and their own.

  Approve, Handled, Reject, the cancellations and every question step but the staff member's answer take no edits (`TakesNoEdits`): refused with the dialog's edits pending and on an absence saved after the decider opened it. No delete: a rejected or canceled absence is kept with its history. Requested and Question have editable fields (Question's for the staff member alone); StaffQuestion is read-only for everyone.

  The state is stored as its number and no check constraint names the states.
- **Rules**, judged by the workflow's conditions (the dialog in memory, the server in the step): who the step's actor is (the runtime's effective user against the staff record's user), what the session may change (the absence guard, `ResourceAbsenceGuard`, an `IStepPreparation` that reads the stored kind and the session's absence permissions), the kind and the period (`AbsenceRules.IsKnownKind`, `AbsenceRules.Problems`), and a staff member in service for a new or an approved one (`StaffServiceRules`: the record and the account active, as the availability reads it).

  A new absence is the row its create inserted, never saved since (`Modified` is null), so Report and Register are refused on a stored one and its Save, Reject and cancellations on a new one.
- **Concurrency.** No rule of an absence reads another row that a concurrent step could change, overlapping absences are allowed, and two steps on one absence (a decision and a cancellation) are put in one order by the transition's own lock (`IsInTransition`, the state concurrency token), so exactly one goes through.

  Every absence step takes the tenant's job lock, as every assignment step does: a request, an assignment, a yes and a pick judge under it whether the staff member is free, so an absence and an assignment of one staff member are judged in one order ([Staffing dialog](features/jobs-and-staffing.md#staffing-dialog)).

### Customer

A customer of the staffing company: a business it staffs jobs for. `TenantStateEntityBase<CustomerState>`, decorated with `[CustomerWorkflow]`; shown in its own dialog (`CustomerDialog`, token `customer`), opened from the Customers page, with a Contacts view whose rows open each contact's own dialog.

- `Name` (max 200, `Customer.NameMaxLength`), unique in its tenant (`IX_Customers_TenantId_Name`, the database's case-insensitive collation; `CustomerService` checks first and answers "Another customer already has this name."), `Description` (max 1000).
- The portal links (ADR 0007), written only by the "Enable portal" step and no field of any state: `LinkedTenantId` (`Guid?`, the managed tenant the customer's portal runs in; a plain column, never a foreign key, as every link across the tenant boundary is; unique where set, `IX_Customers_LinkedTenantId`, since a managed customer tenant has one supplier) and `DefaultUnitId` → OrganizationUnit (NoAction, indexed; the unit of this tenant its portal jobs go to; a unit a customer names is not deleted, `CustomersBlockUnitDelete`, a delete blocker).

  The lock order holds: the staffing company's row, its customer lock, then the new tenant's row and its structure lock, which no other transaction can know of before the commit. Inactive → Deleted is refused while the customer has a portal (`KeepsItsPortalReason`).

### Supplier

- `LinkedTenantId` (`Guid`): the staffing company's tenant, the portal tenant's `ParentTenantId`; a plain column, never a foreign key, as every link across the tenant boundary is; written once (a later change throws); unique per tenant (`(TenantId, LinkedTenantId)`).

### Order

A customer portal's order for a job ([ADR 0007](adr/0007-cross-tenant-ordering-customer-portal.md)): what an orderer asks the staffing company to staff, a row of the portal's own tenant. `TenantStateEntityBase<OrderState>`, decorated with `[OrderWorkflow]`; shown in its own dialog (`OrderDialog`, token `order`), opened from "New order", "My orders" (a row is the order's page, `/portal/orders/{id}`) and the order's page ([Customer portal](features/customers-and-portal.md#customer-portal)).

- `Name` (max 200, `Order.NameMaxLength`, a job's name, required), `Description` (max 2000, a job's): what the job is, as the job it becomes names and describes it.
- `PeriodStart` and `PeriodEnd` (`DateOnly`, calendar days, both included, ADR 0020; check constraint `CK_Orders_PeriodInOrder`); the steps judge the job's own period rules (`JobRules.PeriodProblems`: in order, at most a year), so the job it becomes is valid.
- **Single or recurring**: `Schedule`, `StartTime` and `EndTime` as a job's (a new order proposes Single); a single order's `PeriodEnd` follows from its day and times, a recurring order carries its period only (its weekly times are the coordinator's to add). The steps judge the job's own rules (`JobRules.ScheduleProblems`), and the send copies the kind and the times onto the job. No check constraint, so a draft may be incomplete.
- **Place**: `PlaceName`, `StreetAddress`, `PostalCode` and `City`, each optional and held to the job's lengths (`OrderService.PlaceTooLong`), editable while the order is edited; the send copies them onto the job. An order has no access notes: the customer writes its own instructions in the description.
- `SupplierId` → Supplier (NoAction; the portal's supplier in Active, chosen by the create, never by the dialog, and fixed once saved: changing it throws).
- `OrdererId` → ApplicationUser (NoAction; a user of the portal: who wrote it, the session's effective user as the create judges it, never the dialog's; fixed once saved). Indexed `(TenantId, OrdererId, State)` for "My orders" and the portal's home.
- `CrossTenantId` and `LinkedCrossTenantId` (`Guid?`): the id the order is known by across the boundary (the job's `LinkedCrossTenantId`) and the job's own `CrossTenantId`; new Guids the Send step writes once (`IOrderSender.Link`) and keeps on a later send, never a row's `Id`, never foreign keys, each unique where set. The create refuses an order that sets either (`OrderWorkflowAttribute.NothingSetAheadReason`).
- `State` (`OrderState`: Create 0, Registration 1, Sent 2, and the states that follow the job: Coordinating 3 "Being staffed", Confirmed 4, InProgress 5, Completed 6, CanceledByUs 7, CanceledBySupplier 8, DeclinedBySupplier 9, and CancellationSent 10, "Cancellation sent": the orderer canceled a sent order and the staffing company has not answered yet) and `IsInTransition`. The entry state is 0; Completed and the three cancellations are final.
- **Lifecycle** (`OrderWorkflowAttribute`), every step needing a session inside the order's own tenant (`OwnTenantReason`), the job's name, a valid period and the supplier in Active (`SupplierActiveReason`): Create → Registration ("Save", `order-save-draft`, `OrdersCreate`: the dialog's create, written in the session's own name, `OwnRequestReason`), Registration's save (`order-save`, `OrdersCreate`), Registration → Sent ("Send", `order-send`, `OrdersSend`, confirmed; carries the dialog's edits for a user who may save them, the edit-authority rule).

  In Create and Registration the name, description and period are editable; Sent and every later state keep everything as it was (ADR 0007: no edit after sending).

  A sent order follows its job through system-driven steps (`order-follow-{to}-from-{from}`, no permission, taking no edits): from Sent, Coordinating, Confirmed and InProgress to every state further along (`OrderSync.MovesForward`), DeclinedBySupplier only from Sent and Coordinating, and from CancellationSent to each final state alone (the staffing company's answer); only the handler of the staffing company's job messages runs them, inside the message's delivery, as the portal's system account.

  Entering Confirmed, Completed, CanceledBySupplier and DeclinedBySupplier notifies the orderer.

  The orderer cancels ("Cancel order", `order-cancel-draft`, `-sent`, `-coordinating`, `OrdersCancel`, confirmed, taking no edits) from Registration into CanceledByUs, and from Sent and Coordinating into CancellationSent (`OrderSync.CanceledTo`), never later; a sent order's cancellation queues its integration message to the staffing company in the step's transaction, and the order ends canceled by us once its job was canceled, or completed when the cancellation found the job completed already (the staffing company answers with its job's state).
- **Sending** writes the staffing company's [Job](#job) in the same transaction (its follow-up, `OrderSendFollowUp`): a failure anywhere rolls both tenants back.
- **Following the job**: the staffing company's job messages are found by the order's `LinkedCrossTenantId` (their correlation), and the orderer's cancellation finds the job by the order's `CrossTenantId`; see [IntegrationMessage](#integrationmessage) and [Customer portal](features/customers-and-portal.md#customer-portal).
- **Isolation.** An ordinary tenant row of its portal: filtered, held and stamped like any. Its links to the job are plain ids, so neither tenant reads the other's row by them: the portal never reads the job, and the staffing company never reads the order (`OrderSendTests`); what crosses afterwards crosses as integration messages, delivered in the receiving tenant as that tenant (`OrderSyncTests`).

- **Thread**. `Order` implements `ICommentedEntity`; its one thread is the customer thread (`CommentAudience.Customer`, "Messages with supplier"), once the request was sent: an orderer's comment carries a `CrossTenantId` and crosses to the staffing company; the staffing company's arrive as copies (`AuthorType` `Supplier`, `AuthorSupplierId` the portal's supplier party, `LinkedCrossTenantId` the job comment's id), written by the portal's system account. A request is never deleted, so its thread never blocks a delete.

### OrderLine

One line of an order ([ADR 0027](adr/0027-generic-resource-staffing.md)): a service its staffing company offers in the portal and how many people of it. A link row of the portal's tenant: `ITenantEntity` with no id of its own, keyed `(TenantId, OrderId, OfferedServiceId)`, so an order names a service once.

- `OrderId` → Order (**Cascade**: the order's own rows; an order is never deleted), `OfferedServiceId` → OfferedService (NoAction, indexed), `Count` (1 to 20, `CK_OrderLines_Count`). At most ten lines (`OrderLine.MaxLines`).
- `Order.Lines` is a declared collection of the order's workflow (`OrderWorkflowAttribute.AreaLines`): hidden in Create, editable in Registration (a draft), read-only from Sent on. The draft's save and its send judge the lines (`LinesValidReason`: each names a copy of the order's own supplier, 1 to 20 people), and the send each copy still offered (`LinesOfferedReason`, naming the portal's copy of each one withdrawn); `OrderService` judges first, a line added anew only for an offered copy. An order without lines is sent too: the coordinator decides the people.
- **Sending** makes one active slot of the staffing company's job per person of every line, each made from the staffing company's own service (`ServiceSlotRules.Build`: its name, description and active qualifications at their levels, `JobSlot.ServiceId` its service), stamped with its system account, its history starting with the system's `slot-receive` out of the entry state (Create → Active, recorded on the staffing company's behalf, never run through the engine, as the job's own receive); a line's slots are alike, so one slot group.

  The send reads the staffing company's services by their cross-tenant ids under its lease and refuses the whole step when one is no longer active and offered (`OrderSendFollowUp.ServiceWithdrawn`).

Read through the lookup cache (`OrderService.OfferedCatalogue`), dropped once a delivery has committed.

### CustomerContact

A person at a customer the coordinator deals with. `TenantStateEntityBase<CustomerContactState>`, decorated with `[CustomerContactWorkflow]`; shown in its own dialog (`CustomerContactDialog`, token `contact`), opened from its customer's Contacts view.

- `CustomerId` → Customer (NoAction: a contact is a state entity, deleted through its own workflow when its customer is; never changed once saved), indexed `(CustomerId, State)` for the Contacts view and the counts on the Customers page.
- `FirstName` and `LastName` (max 100 each, required), `Email` (max 256), `Phone` (max 50), `Title` (max 100).
- `LinkedUserId` (`Guid?`): the portal orderer the contact stands for, a user of the customer's managed tenant; a plain column, never a foreign key (ADR 0007), unique where set (`IX_CustomerContacts_LinkedUserId`); no field of any state.

  Nothing keeps the contact's names in step with the user's afterwards (ADR 0007: linked identity sync is left for later); the coordinator edits the contact as any other.
- `State` (`CustomerContactState`: Create 0, Active 1, Inactive 2, Deleted 3) and `IsInTransition`.
- **Lifecycle** (`CustomerContactWorkflowAttribute`), every step needing `CustomersManage` and a session inside the contact's own tenant: Create's save (the state's save step; in the dialog's create mode the step that adds it; refused while the customer is inactive, `CustomerNotInactiveReason`), Create → Active (activate, needing an active customer, `CustomerActiveReason`; the services take it as the create too), Create → Deleted (delete, confirmed), Active's save (the state's save step), Active → Inactive (deactivate, confirmed; also taken by the customer's deactivation), Inactive → Active (reactivate, needing an active customer), Inactive → Deleted (delete, confirmed, when no registered delete blocker reports use).

  In Create and Active the names, e-mail address, phone and title are editable; Inactive keeps everything as it is.

### Job

A job the staffing company staffs for a customer ([ADR 0006](adr/0006-course-staffing-domain.md)). `TenantStateEntityBase<JobState>`, decorated with `[JobWorkflow]`; shown in its own dialog (`JobDialog`, token `job`), opened from the Jobs page, with Info, Timetable and Slots views ([Jobs, timetable and slots](features/jobs-and-staffing.md#jobs-timetable-and-slots)).

- `Name` (max 200, `Job.NameMaxLength`, required), `Description` (max 2000).
- `CustomerId` → Customer (NoAction; a customer jobs are registered for is not deleted, `JobsBlockCustomerDelete`), `ContactId` → CustomerContact (optional, NoAction; one of the job's customer's own contacts, judged by every step; `JobsBlockContactDelete`), `OrganizationUnitId` → OrganizationUnit (NoAction; the Company root unless another unit in use is chosen, ADR 0021; `JobsBlockUnitDelete`), each indexed by its foreign key.
- `PeriodStart` and `PeriodEnd` (`DateOnly`, calendar days of the tenant, both included, ADR 0020; check constraint `CK_Jobs_PeriodInOrder`); a period lasts at most a year (`JobRules.MaxPeriodDays`, 366), which the steps judge.
- **Single or recurring** ([ADR 0027](adr/0027-generic-resource-staffing.md)): `Schedule` (`JobSchedule`: Single 1, Recurring 2; Recurring for a row written without it, while the dialog proposes Single), `StartTime` and `EndTime` (`TimeOnly?`).

  A single job's day is `PeriodStart`, its `PeriodEnd` the day it ends, stored and derived (`JobRules.Normalize`: the next day when its end is at or before its start), so every query that pre-filters by period stays right, and it has no weekly times; a recurring job has its period and weekly times and no times of its own.

  Check constraint `CK_Jobs_ScheduleTimes` holds a single job's two times (never equal, ending on its day or the next) and a recurring job's none; the steps judge the whole rule in words first (`JobRules.ScheduleProblems`, the workflow's schedule condition). The kind and the times are edited where the period is (until the job is confirmed).

  Every reader of time reads a job's occurrences through one rule (`JobRules.Occurrences(JobTimes, …)`, an occurrence past midnight cut into its days by `JobRules.DaySegments` for the readers that work by day), and the job clock moves a job by its instants (`JobRules.Window`: a single job at its start and end times).
- **Place**: `PlaceName` (max 200, `Job.PlaceNameMaxLength`), `StreetAddress` (max 200), `PostalCode` (max 20), `City` (max 100) and `AccessNotes` (max 1000), each optional, trimmed and a blank one stored as none; a part over its length is refused (`JobService.PlaceTooLong`).

  The workflow's Place area (`JobWorkflowAttribute.AreaPlace`, the dialog's Place view) is editable wherever the description is (Create through InProgress) and read-only once the job is completed, canceled or deleted; no step requires a place. `JobPlace` reads the four parts of the place and never the access notes.

  The access notes reach the job's readers and the staff member whose own assignment is Assigned: the assignment service blanks them on a staff member's own load in any other state (`SlotAssignmentService.LoadSlotAssignmentUpdaterAsync`), and nothing of them crosses to a portal.
- `CoordinatorUserId` → ApplicationUser (optional, NoAction): set by the step into Coordinating to the user who takes it (an action of `job-start` and `job-start-from-registration`), never by a dialog (no state makes it editable).
- The cross-tenant links ([ADR 0007](adr/0007-cross-tenant-ordering-customer-portal.md)), set only on a job a portal sent and no field of any state: `CrossTenantId` (`Guid?`, the id the job is known by across the boundary; a column of its own, never the row's `Id`: a new Guid written once as the job first crosses, so the customer's tenant never learns the job's own key) and `LinkedCrossTenantId` (`Guid?`, the customer tenant's request it was sent from); plain columns, never foreign keys, each unique where set.

  The registration refuses a new job that sets either, or a coordinator (`JobWorkflowAttribute.NothingSetAheadReason`), so no user's create reaches the unique index; a portal's send writes them through its own path ([Order](#order)): the job's `CrossTenantId` is the request's `LinkedCrossTenantId` and its `LinkedCrossTenantId` the request's `CrossTenantId`, so a send again finds the job by them and writes no second one.
- **Received from a portal**.

  A [Order](#order)'s Send writes the job straight into AwaitingCoordination on the staffing company's behalf, in the send's transaction under the tenant's structure, customer and job locks: on the customer's `DefaultUnitId`, with the orderer's paired contact, the request's name, description and period, and the link ids; created by the tenant's system account with no impersonator, its first history entry `job-receive` (Create → AwaitingCoordination, "Received", a system-driven step no user takes and no public path runs) with that account as its actor, and a notice to every holder of `PerformCoordination` (`job-requested`).

  It has no times and no slots yet: the coordinator completes them, as AwaitingCoordination allows, before starting it.
- **Telling its portal**.

  A job that carries a `CrossTenantId` keeps its customer (`PortalCustomerKeptReason`), and every step into a customer-visible state from another (Coordinating, Confirmed, InProgress, Completed, CanceledByCustomer, CanceledBySupplier, Deleted: `OrderSync.Table`) queues one [IntegrationMessage](#integrationmessage) of kind `job-state` to its customer's portal in its own transaction (`IJobStateSync`), with its assigned staff members' names from the confirmation on; so does an assignment step that gives a confirmed or running job a staff member or takes one away.

  Registration and AwaitingCoordination queue nothing.

  The orderer's cancellation comes back as `order-cancel`, whose handler runs the system-driven step "Canceled in the portal" (`job-canceled-in-portal-{state}`, from every state a job is canceled from into CanceledByCustomer, no permission, taking no edits) inside the message's delivery as the tenant's system account: the slots and their live assignments are canceled with it, each staff member told, and the job's coordinator is told (`job-canceled-in-portal`; every holder of `PerformCoordination` while it has none, one whose account is no longer active, or one who no longer holds `ViewCoordination`, judged as the notice is delivered through its `FallbackPermission`).

  A cancellation that finds the job completed or canceled already leaves it as it is and answers the portal with the job's state (`IJobStateSync.QueueAnswerAsync`), so the request, "Cancellation sent" meanwhile, ends where the job did.
- `State` (`JobState`: Create 0, Registration 1, AwaitingCoordination 2, Coordinating 3, Confirmed 4, InProgress 5, Completed 6, CanceledByCustomer 7, CanceledBySupplier 8, Deleted 9) and `IsInTransition`. The entry state is 0: a job written without naming a state is one nobody registered. Indexed `(TenantId, State, PeriodStart)` for the Jobs page and the coordination workspace.
- `Attributes`: the job's custom-field values (`JobAttribute`; [Entity attributes](#entity-attributes)), owned rows deleted with the job, a declared collection of the workflow's custom fields area (editable until the job is completed or canceled).
- **Lifecycle** (`JobWorkflowAttribute`): Create → Registration (register, `JobsCreate`: the dialog's create), Registration's save, Registration → AwaitingCoordination (hand over, `JobsCreate`), AwaitingCoordination's save, AwaitingCoordination → Registration (back, `JobsEdit`), AwaitingCoordination → Coordinating and Registration → Coordinating (start coordination, `PerformCoordination`, naming the coordinator), Coordinating's save, Coordinating → Confirmed (confirm, `PerformCoordination`, confirmed; not guarded on coverage), Confirmed's and InProgress's saves; every save `JobsEdit`.

  Confirmed → InProgress (`job-period-starts`, "Period started") and InProgress → Completed (`job-period-ends`, "Period ended") are the job clock's system-driven steps (no permission, since no user takes them and every public path refuses them): the first from the start of the period's first day, the second once its last day is over, both judged on the job's own tenant's calendar (the job guard reads the tenant's time zone before the steps are judged), each with a history row whose actor and stamp are the tenant's system account.

  Registration → Deleted (`job-delete`, `JobsDelete`, confirmed) removes a job nobody was asked to work (`JobWorkflowAttribute.NoStaffAskedReason`, read over its slots' assignments) with its slots, each through its own system-driven step into Deleted, its times and its custom-field values: the row goes (ADR 0016), so the customer, contact and unit blockers, which count every stored job, never count a deleted one.

  Registration, AwaitingCoordination, Coordinating, Confirmed and InProgress → CanceledBySupplier (`job-cancel-<state>`, "Cancel job") and → CanceledByCustomer (`job-canceled-by-customer-<state>`, "Canceled by the customer"), each `JobsCancel`, confirmed and taking no edits: both cancel states cascade into the active slots' Cancel, which cancels their live assignments, each through its own step with its history and its notice.

  Every step needs a session inside the job's own tenant (`JobWorkflowAttribute.OwnTenantReason`).
- **Fields per state.** Until coordination starts (Create, Registration, AwaitingCoordination) everything is edited, the customer included; in Coordinating the customer is fixed; once Confirmed (and InProgress) the period, the timetable and the slots are fixed, and the name, description and contact are kept up to date. The finished, canceled and deleted states are read-only, custom fields included.
- **Rules** (judged by the steps' conditions, the dialog in memory, the server in the step):
  - the name, customer and unit given;
  - the period and the weekly timetable valid (`JobRules`: the period in order and at most a year; each time on a weekday, starting before it ends, overlapping no other time of its day, adjacent ones allowed);
  - the contact one of the job's customer's;
  - a customer, contact or unit the step chooses anew in use (an active customer, an active contact, the Company root or an active unit), while one the stored job names already is kept whatever has become of it (the job guard, `IJobGuard`/`JobGuard`, an `IStepPreparation` that reads what the stored job names before the step's edits; a job nothing was read for is not judged, fail closed).

  Handing over and starting need the customer, contact and unit in use now, a time in the timetable and an active slot; confirming needs a time. Handing over, starting and confirming need the job's required custom fields filled (`RequiredAttributesCondition`). A reference the step reads is the row its key names, never a navigation the caller built.
- **Staff are staffed** while the job is Coordinating, Confirmed or InProgress (`JobRules.StaffingOpen`); its slots change while it is Registration, AwaitingCoordination or Coordinating (`JobRules.SlotsOpen`).
- **Coverage** (uncovered, partly covered, covered) is derived from its active slots and their assignments, never stored (ADR 0006): `JobCoverageRules` judges, `JobCoverageReader` reads many jobs and slots in two queries (the slots, then the held ones among them); a slot is held by an Assigned or Accepted assignment of a staff member in service (`StaffServiceRules.InService`, so a staff member taken out of service leaves their slot uncovered while the assignment stays), counted once however many staff members said yes.
- **One writer at a time per tenant.** Every job step takes the tenant's structure lock, then its customer lock, then its job lock (`AppLock.Structure`, `AppLock.Customers` and `AppLock.Jobs`, taken in rank order), each holding the tenant's row first: a unit's delete and deactivation, a customer's or contact's deactivation and delete, and a slot's steps are each put in one order with the job steps that judge them. A lock not granted in time refuses the step with its busy reason (`AppLockBusyException`).
- **Internal thread** (ADR 0010). `Job` implements `ICommentedEntity`; its internal thread (`CommentAudience.Internal`) holds the coordinators' notes, read with `ViewCoordination` and written with `PerformCoordination`, never notified, and each cancellation's reason (the cancel steps' prompts); a job whose thread holds a note is not deleted (`CommentThreadsBlockDelete`).
- **Customer thread** (ADR 0010). A job a portal sent has its customer thread too (`CommentAudience.Customer`), read with `ViewCoordination` and written with `PerformCoordination`: a coordinator's comment there carries a `CrossTenantId` and crosses to the portal; the customer's arrive as copies (`AuthorType` `Contact`, `AuthorContactId` the contact the writer is paired with, `LinkedCrossTenantId` the portal comment's id), written by the staffing company's system account. A job no portal sent has none.

### JobTimeSlot

One weekly time of a job's timetable. An owned row without a lifecycle (`TenantEntityBase`: a tenant row like every other).

- `Weekday` (`Weekday`: Monday 1 to Sunday 7, ISO numbering; check constraint `CK_JobTimeSlots_Weekday`), `Start` and `End` (`TimeOnly`, local times of the tenant's zone, ADR 0020; check constraint `CK_JobTimeSlots_StartBeforeEnd`).

### JobSlot

One person a job needs: a crew of three is three slots. `TenantStateEntityBase<JobSlotState>`, decorated with `[JobSlotWorkflow]`; shown in its own dialog (`JobSlotDialog`, token `slot`), opened from its job's Slots view.

- `JobId` → Job (NoAction: a slot is a state entity, deleted through its own workflow with a deleted job; never changed once saved), indexed `(JobId, State)`.
- `Name` (max 100, required), `Description` (max 1000).
- `State` (`JobSlotState`: Create -1, Active 0, Canceled 1, Deleted 2) and `IsInTransition`. The entry state is Create: slots are added by count through its one step, Create → Active (`slot-add`, `JobsEdit`, the save's conditions plus a count of 1 to `JobSlotRules.MaxAddCount` = 20), each slot a row of its own with its own history, all of one add in one transaction sharing one correlation id (`WorkflowService.CreateManyAndTransitionAsync`). `Count` (`[NotMapped]`, ignored by the model) is asked only in Create.
- **Slot groups**. Active slots of one job alike in name (trimmed, case ignored), service (`ServiceId`, none for a slot made by hand) and qualifications at their levels form a slot group (`SlotGroups`, `SlotGroupKey`, `Staffora.Core/Jobs/SlotGroups.cs`), derived on every read and never stored; its members ordered by `Created`, then `Id`, the first its representative.

  Another service, or a qualification Preferred where another slot requires it, splits a group. A copy of a slot (`JobSlotService.NewJobSlotAsync(jobId, copyOf)`: its name, description, service and qualifications at their levels) joins its group.
- **Lifecycle** (`JobSlotWorkflowAttribute`), every step needing `JobsEdit` and a session inside the slot's own tenant: Active's save (the state's save step; in the dialog's create mode the step that adds the slot), Active → Canceled ("Cancel slot", `slot-cancel`, confirmed, `TakesNoEdits`).

  Both only while the job takes slots (`JobSlotWorkflowAttribute.JobTakesSlotsReason`, read from the job the slot's key names), or, for the Cancel, as part of its job's cancellation, whatever the job's state (`WorkflowContext.IsTakenWith`). Active → Deleted and Canceled → Deleted (`slot-delete-with-job`, `slot-delete-canceled-with-job`) are system-driven, taken only through the job's delete.

  Canceled cascades into the slot's live assignments: each Requested, Accepted or Assigned one takes its own cancel step, with its history (correlated with the slot's) and its notice to its staff member, so whoever cancels a slot with live assignments needs `PerformCoordination` too; a Declined or NotSelected one stays. Every step takes the tenant's job lock.

  A slot staff members were asked for is not deleted (`AssignmentsBlockSlotDelete`, which counts its assignments): it is canceled.
- `Qualifications`: `JobSlotQualification` rows, a declared collection of the workflow's Qualifications area (editable while active).
- `ServiceId` → Service (NoAction, nullable, indexed `(TenantId, ServiceId)`): the service of the catalogue the slot was made from, set as it is created and never changed (`PropertySaveBehavior.Throw`, read-only in every state). Its save refuses a service named anew that is not Active (`JobSlotWorkflowAttribute.ServiceActiveReason`, under the job lock every service step takes too; the service asks first, `JobSlotService.ServiceNotActive`).

  The service is a template: a slot made from it takes its name, description and qualifications at their levels (`ServiceSlotRules`), and later changes to the service never reach it.
- `Assignments`: the slot's `SlotAssignment` rows, each a state entity of its own, loaded with the slot's workflow graph with their staff records and users (its Cancel's cascade tells each staff member), and listed in the slot dialog's Staff view.
- `Rounds`: the `RequestRound` rows sent from the slot; a slot with rounds is not deleted (`RoundsBlockSlotDelete`).

### JobSlotQualification

A qualification a slot requires. A link row: `ITenantEntity` with no id of its own, keyed `(TenantId, JobSlotId, QualificationId)`, with the audit columns of every tenant row.

- `JobSlotId` → JobSlot (**Cascade**: the slot's own rows, deleted with it), `QualificationId` → Qualification (NoAction, indexed; a qualification is never deleted).

  Saved with the slot through its updater; a qualification required anew is an active one of the catalogue, judged by the slot's save itself (`JobSlotWorkflowAttribute.QualificationActiveReason`, over the qualifications its graph loads, under the job lock every qualification step takes too; the service asks first for its own message), and an archived one stays on the slots that required it before, still counted as required.

A missing Required qualification is a warning; a Preferred one only ranks the candidates (`StaffingRules.MatchAtLevels`, `RankFacts.PreferredMatching`) and never warns, so the week board and the planning verdicts read the Required rows only.

### TenantRole

A role defined per tenant. A state entity: `TenantStateEntityBase<TenantRoleState>`, decorated with `[TenantRoleWorkflow]`.

- `Name` (max 100, `TenantRole.NameMaxLength`), `Description` (max 500, `DescriptionMaxLength`)
- `State` (`TenantRoleState`: Create 0, Active 1, Deleted 2) and `IsInTransition`. Only an Active role grants its permissions and is given to anyone; the entry state is 0, so a role written without naming a state grants nothing, and every path that writes a role in use names Active itself (the seeding, the end-to-end fixture, the workflow's create step).

One row per permission: unique index `IX_TenantRolePermissions_TenantId_TenantRoleId_Permission` (`TenantRolePermissionConfiguration.OnePerPermissionIndex`), so two writers adding the same permission at once store it once.

  The System owner role's are kept complete at every start (`SystemOwnerPermissionsEnsure`: every grantable permission outside own work, one a release adds included, stamped with the tenant's system account, for the tenants in Setup, Active and Suspended; [Authorization](authorization.md#system-owners)).

Because `RolePermission` is stored as its integer value, append new members and keep existing values unchanged.

### StateHistoryEntry

One state change of one state entity, written by `StateHistoryWriter.Add(context, outcome)` (`Staffora.Data/StateHistoryWriter.cs`) from the engine's `TransitionOutcome` and saved with the transition. `TenantEntityBase`; the entity's tenant (a tenant's own lifecycle is recorded in that tenant).

- `EntityType` (max 100, the model's type name), `EntityId` (`Guid`), `TransitionKey` (max 100), `FromState` and `ToState` (the state enum's explicit `int` values)
- `CorrelationId`: shared by every entry one transition wrote, cascaded children included; by default the primary entity's entry id
- `ActorId`: the effective user who ran the transition. No foreign key, so an actor from outside the tenant (a platform owner moving a tenant) can be recorded here, while `CreatedById` must be a user of the entry's tenant. An entry of the runtime's own tenant is stamped with the actor; an entry of another tenant (a platform owner moving a tenant in system scope) is written on that tenant's behalf, so the writer sets `CreatedById` to that tenant's system account
- No foreign key to the entity ([ADR 0016](adr/0016-deletion-cascades-through-child-workflows.md)): an entry outlives a hard delete, and one table serves every state entity
- Never rewritten: `SaveChanges` refuses any update of an entry, and its delete outside system scope

### CommentContainer

One comment thread: the comments of one audience on one commented record ([ADR 0010](adr/0010-comment-threads-per-audience.md)). `TenantEntityBase`; the record's tenant. A record is commented when it implements `ICommentedEntity` (`Staffora.Core/Entities/Comments/`: a tenant row with a `Guid Id`), which needs no column of its own.

- `EntityType` (max 100, the model's type name, as the state history names it), `EntityId` (`Guid`), `Audience` (`CommentAudience`: `Internal` 0, `Staff` 1, `Customer` 2; who the thread is for, never a flag on a comment)
- Created with its first comment by `CommentThreadWriter` (`Staffora.Data/CommentThreadWriter.cs`), the one place a thread or a comment is constructed; a record nobody wrote on has none
- Unique `(TenantId, EntityType, EntityId, Audience)`: one thread per record and audience.

  One writer at a time per record: every writer takes the record's thread lock (`CommentThreadWriter.LockAsync`, `AppLock.CommentThread`, owned by its transaction) before it looks for the thread, so two first comments at once (two posts, or a post and a step's note) create one thread and both are stored; the delete blocker counts under the same lock, and a post holds the record's row (repeatable read) from its read to its commit, taking the row before the lock as a step does, so a delete and a first comment never leave a thread without its record and never wait on each other in a ring
- No foreign key to the record, like the state history; a record whose threads hold a comment is not hard deleted (`CommentThreadsBlockDelete`, an `IDeleteBlocker` for every `ICommentedEntity`), so no thread is left without its record
- Never rewritten: `SaveChanges` refuses an update of a thread, and its delete outside system scope

### Comment

One comment of a thread. `TenantEntityBase`; its thread's tenant.

- `CommentContainerId` (FK to `CommentContainers`, `NoAction`), `AuthorType` (`CommentAuthorType`: `User` 0, `System` 1, `Contact` 2 and `Supplier` 3 for a copy that crossed from the other tenant of the customer thread), `Kind` (`CommentKind`: `Comment` 0, written in the thread; `TransitionNote` 1, a step's comment prompt answered), `TransitionKey` (max 100, the step a note explains; null otherwise), `Text` (max `Comment.MaxTextLength`, 2000; trimmed, never blank)
- The customer thread's columns (ADR 0007): `CrossTenantId` (`Guid?`, unique where set) on a comment posted there, the id its copy in the other tenant names, a new Guid never the row's `Id`; `LinkedCrossTenantId` (`Guid?`, unique per tenant where set, `IX_Comments_TenantId_LinkedCrossTenantId`) on a copy, the id of the comment it copies, so a comment is copied at most once; `AuthorContactId` → CustomerContact and `AuthorSupplierId` → Supplier (`NoAction`, nullable), the copy's author as its own tenant knows them.

  A contact who wrote is not deleted (`CommentsBlockContactDelete`); a supplier party is never deleted.
- The author is the creator (`CreatedById`, the effective user stamped by `SaveChanges`) for a `User` comment, and the time its `Created` stamp (UTC from the injected clock, ADR 0020); no author column repeats them. A note a platform owner's step writes into another tenant is stamped with that tenant's system account, as the step's other rows are
- Never edited or deleted (ADR 0010): `SaveChanges` refuses an update in every scope and a delete outside system scope, and `BulkUpdateGuard` refuses either bulk statement in every scope

### OutgoingMessage

A notice a step queued ([ADR 0011](adr/0011-notifications-from-workflow-after-commit.md)): the messaging pipeline's outbox. `TenantEntityBase`; the tenant whose entity the step moved. Written by `OutgoingMessageWriter` (`Staffora.Data/`) in the step's transaction (TRANSITION-ORCHESTRATION.md, step 10), so a rolled-back step leaves none; delivered after the commit by the dispatcher ([Notifications](features/notifications-and-comments.md#notifications)).

- `MessageType` (max 100, the `MessageType` key), `Category` (`MessageCategory`: `Account` 0, `Staffing` 1, `Absence` 2, `Ordering` 3, `Conversation` 4), `EntityType` (max 100, the model's type name), `EntityId` (`Guid`), `HistoryEntryId` (`Guid`, the step's primary history entry), `Subject` (max 200), `Text` (max 2000), `Link` (max 500, a local address, nullable): the words as filled from the entity when the step ran (`MessageCatalogue`)
- `RecipientUserIds` (the named people, a JSON array of ids in one column of at most 4000 characters, at most 100 ids) and `RecipientPermission` (`RolePermission`, nullable: every active holder in the tenant receives it too)
- `NamedRecipientsHold` (`RolePermission`, nullable): when set, a named person receives the notice only while they hold that permission in the tenant as it is delivered (a staff member's answer reaches the coordinators who asked only while they coordinate)
- `FallbackPermission` (`RolePermission`, nullable): when set, every active holder in the tenant receives the notice when the named people resolve to nobody as it is delivered (none named, none active, none holding `NamedRecipientsHold`): a portal's cancellation and a customer's message reach every coordinator when the job's own no longer could read them, and a staffing company's message the portal's customer administrators when the orderer could not
- `Status` (`OutgoingMessageStatus`: `Pending` 0, `Delivered` 1, `Failed` 2), `Delivered` (UTC, nullable), `RecipientCount`: a plain column, not a workflow (delivery is the pipeline's bookkeeping, ADR 0011); a failed delivery is marked `Failed` and logged.

  `Attempts` (int, a concurrency token) and `NextAttempt` (UTC, nullable): the hosted dispatcher's retry, which takes a `Failed` row once `NextAttempt` has come and a `Pending` one a minute after it was written, each only while its tenant's data is not held, claims it (one more attempt, `NextAttempt` the claim's end) and gives it up (`Failed`, `NextAttempt` null) after eight; an index `(Status, NextAttempt)` finds them
- After it is written only its delivery's columns change (`Status`, `Delivered`, `RecipientCount`, `Attempts`, `NextAttempt`, `ApplicationDbContext.NoticeBookkeepingColumns`): `SaveChanges` refuses any other change in every scope and a delete outside system scope, and `BulkUpdateGuard` refuses a bulk delete and a bulk update of any other column, so a notice is never reworded or readdressed after its step committed
- No foreign key to the entity or the history entry, like the state history; index `(TenantId, HistoryEntryId)` for a page of history's notices, index `(TenantId, Status)` for the rows still to deliver

### StoredMessage

A notice as the in-app channel delivered it. `TenantEntityBase`; its outgoing message's tenant. Written once by `InAppChannelSender`, with its recipients and the outgoing message's status in one save; nothing in the app changes it afterwards, and only the retention pass deletes it, in system scope, once none of its copies is left and it is older than the notices' period ([Retention](features/operations.md#retention)): `SaveChanges` refuses an update in every scope and a delete outside system scope, and `BulkUpdateGuard` refuses either bulk statement in every scope but the tenant purge's.

- `OutgoingMessageId` (FK to `OutgoingMessages`, `NoAction`, unique: a delivery run twice delivers once), and a copy of its words and links: `MessageType`, `Category`, `Subject`, `Text`, `Link`, `EntityType`, `EntityId`, `HistoryEntryId`, with the outgoing message's lengths

### MessageRecipient

One person's copy of an in-app notice. `TenantEntityBase`; its message's tenant.

- `StoredMessageId` (FK to `StoredMessages`, `NoAction`), `UserId` (FK to `AspNetUsers`, `NoAction`: a user of the same tenant, which the data context's reference check holds), `IsRead`, `ReadAt` (UTC, nullable)
- The read flag is a plain column, not a workflow (ADR 0011, a deliberate exception to ADR 0009); only its own user marks it read, through `NoticeService` (one bulk `UPDATE` of the reader's own unread copies, allow-listed), never while impersonated ([Authorization](authorization.md#notices))
- Only `IsRead` and `ReadAt` change after it is written: `SaveChanges` refuses a change of any other column (its user, its message) in every scope and a delete outside system scope; `BulkUpdateGuard` refuses a bulk delete and a bulk update that sets anything but `IsRead`, `ReadAt` and the editor stamp
- Removed by the retention pass in system scope once read longer ago than `Retention:ReadNoticeDays` (180 days); an unread copy is never removed ([Retention](features/operations.md#retention))
- Unique `(StoredMessageId, UserId)`; index `(TenantId, UserId, IsRead)` for a person's unread count and newest notices

### IntegrationMessage

A message one tenant sends a linked tenant through the integration outbox ([ADR 0007](adr/0007-cross-tenant-ordering-customer-portal.md)): what crosses the boundary after a portal request was sent. `TenantEntityBase`; the **sending** tenant's row, queued by `IntegrationOutbox.Enqueue` (`Staffora.Data/`) in the sender's own step transaction (a rolled-back step sends nothing; a tenant sends nothing to itself), and delivered by the hosted dispatcher ([Integration outbox](features/operations.md#integration-outbox)).

- `Sequence` (`long`, an identity column, unique): the order the outbox was written in; a correlation's messages go in this order. The steps that queue hold their record's lock (a job's under its job lock), so the order they commit in is the order they were numbered in.
- `Kind` (max 100, the key its handler is registered under), `TargetTenantId` → Tenant (NoAction; `Tenant` belongs to no tenant, so no row of another tenant is named), `CorrelationId` (`Guid`, what it is about across the boundary, a job's cross-tenant id), `Payload` (max 4000, JSON: what the sender chose to expose).

  The kinds: `job-state` (`OrderSync`, a staffing company's job to its portal, correlated by the job's `CrossTenantId`: the job's state, whether it had been confirmed, and from the confirmation on its staff members' names), `order-cancel` (`OrderSync`, a portal to its staffing company, correlated by the request's `CrossTenantId`, an empty payload), `job-comment` and `order-comment` (`JobThreadSync`, the customer thread's comments each way), and `service-offered`, `service-changed` and `service-withdrawn` (`ServiceOfferSync`, a staffing company's portal services to its portals)
- `State` (`IntegrationMessageState`: `Pending` 0, `Delivered` 1, `DeadLettered` 2), a plain column, not a workflow (delivery is the dispatcher's bookkeeping, as a notice's is)
- `Attempts`; `NextAttempt` (UTC, when it is next due: when written, then after each failure 30 seconds doubling to at most an hour, `IntegrationRetryRules`); `ClaimToken` (`Guid?`, a concurrency token renewed on every claim, so a dispatcher whose claim lapsed and was taken over writes nothing) and `ClaimedUntil` (UTC, the claim's two-minute lease); `Finished` (UTC, delivered or given up); `LastFailure` (max 200: the failure's kind or a refusal's fixed reason, never the failure's details, which arose in the other tenant and stay in the platform's error log)
- Queued only by `IntegrationOutbox.Enqueue` (a source scan allows `new IntegrationMessage` nowhere else) and never under a lease, where the runtime's tenant need not be the sender; inserted only new (pending, no attempt, claim, end or failure), in every scope
- Delivered only between linked tenants (`Tenant.ParentTenantId`, `TenantStates.AreLinked`, never the platform tenant; otherwise a dead letter at once, nothing written), only while both tenants are Active (`TenantStates.ExchangesMessages`; otherwise held, no attempt spent), after every earlier pending message of its sender's correlation; a dead letter after eight attempts no longer holds the next one up
- After it is written only its delivery's columns change (`State`, `Attempts`, `NextAttempt`, `ClaimToken`, `ClaimedUntil`, `Finished`, `LastFailure`; `ApplicationDbContext.NoticeBookkeepingColumns`): `SaveChanges` refuses any other change in every scope, any change of those outside system scope (only the dispatcher writes them, under its leases, never the sender's own session) and a delete outside system scope, and `BulkUpdateGuard` refuses either bulk statement in every scope, so nothing a message carries is rewritten after its step committed
- Removed by the retention pass in system scope, a batch at a time, once Delivered and `Finished` longer ago than `Retention:ProcessedOutboxDays` (30 days); a pending message or a dead letter is never removed, and a tenant's purge removes the messages other tenants sent it ([Retention](features/operations.md#retention))
- Index `(State, NextAttempt)` for what is due, index `(TenantId, CorrelationId, Sequence)` for a correlation's earlier messages

### IntegrationReceipt

That an integration message was handled. `TenantEntityBase`; the **receiving** tenant's row, written only by the handler registry (`IntegrationHandlerRegistry.HandleOnceAsync`; a source scan allows `new IntegrationReceipt` nowhere else, so none is written ahead of its message) in the delivery's transaction, with the handler's own writes and before the sender's message is marked, stamped with the receiving tenant's system account.

- `MessageId` (`Guid`, the outbox row's id: a link across the boundary, never a foreign key; the row exists only to cross and names no record of the sender), `Kind` (max 100)
- Unique `(TenantId, MessageId)` (`IX_IntegrationReceipts_TenantId_MessageId`): a message is handled at most once in its tenant. A delivery that finds its receipt runs no handler (its mark was lost), and of two deliveries at once only one commits
- Never changed once written: `SaveChanges` refuses an update in every scope and a delete outside system scope, and `BulkUpdateGuard` refuses either bulk statement
- Removed by the retention pass in system scope once older than `Retention:ProcessedOutboxDays`, unless a message of its id is still pending or a dead letter, whose retry it keeps from running twice ([Retention](features/operations.md#retention))

### ApplicationUser

`IdentityUser<Guid>`, an `ITenantEntity` (ADR 0012, ADR 0013) and a state entity (`IStateEntity<UserState>`, the user workflow `ApplicationUserWorkflowAttribute`): every user belongs to exactly one tenant, platform owners to the platform tenant and a system account to the tenant it acts for, and users are filtered and stamped like every tenant row. Its configuration calls `ConfigureTenantEntity()`, so the audit columns point back at the users themselves.

- `FirstName`, `LastName` (max 100, required)
- `State` (`UserState`: Create 0, Active 1, Inactive 2) and `IsInTransition`, the concurrency tokens of every state entity, beside Identity's own `ConcurrencyStamp`, which every write of the row renews (`ApplicationDbContext`), so a copy Identity read before a step is refused rather than written back over it.

  The entry state is 0, the default, so a user written without naming a state fails closed: in Create nobody signs in, is impersonated or holds a role that grants anything.

  Every path that writes a user in use names Active itself (the seeder, the bootstrap, a system account, the browser journeys' preparation); outside system scope a user is inserted only in Create, by the create step, and Identity's own create is refused from any session with a signed-in user. Only an Active user signs in, is impersonated and holds roles that grant anything.

  A user has no delete step and is never deleted: the data context refuses removing a state entity outside its delete transition (ADR 0016), so a user is deactivated instead.
- Field access by state (the workflow): the person's fields (names, email, user name, phone) and the custom fields are edited in Create and Active, the four identifying ones required there, and kept as they were while Inactive; Identity's own columns (password hash, stamps, normalized name and address, confirmations, two-factor, lockout and counters) and `LastSignedIn` are editable in every state, so Identity is never refused for the state, and the user dialog's updater never writes them (`DetachedEntityUpdaterOptions.Excluding`; the concurrency stamp is compared with the database as the updater saves and renewed by it).

  Everything else (`IsSystemAccount`) is read-only in every state, so no edit changes it.
- `LastSignedIn`: when the user last signed in (UTC), null until they do; sign-in bookkeeping like the failed-attempt count, written by `ApplicationSignInManager` as it issues a sign-in cookie (not by a refresh or an impersonation), stamped with the tenant's system account (`ApplicationUserStore.SignInBookkeepingColumns`), shown on the platform console's user list
- `IsSystemAccount`: the tenant's system account (below)
- `TenantId` (`Guid`, required, read-only after save) with `Tenant` navigation (NoAction), and its index
- `UserName` and `Email` are unique across every tenant (Identity's unique `UserNameIndex`; `EmailIndex` on `NormalizedEmail`, unique and filtered to users with an address, since a system account has none), because sign-in finds a user by either before any tenant is known.
- `Created`, `CreatedById`, `Modified`, `ModifiedById`, `ImpersonatedById`: a user written by a person of their own tenant (an administrator creating, renaming or resetting a colleague; nobody changes their own account, [ADR 0034](adr/0034-no-self-service-account-pages.md)) names that person; a user written on a tenant's behalf with nobody of the tenant acting (the seeder, the bootstrap, the platform console) is created or edited by that tenant's system account, and so is every sign-in bookkeeping write (failed attempts, lockout, their reset), whoever the circuit's user is, since it is a sign-in's record and not anyone's edit.

  A system account is its own creator.
- `Attributes`: custom field values

**Finding users before a tenant is known.** Identity resolves a user before any tenant is known (sign-in by name or email; the cookie and its revalidation by id), so its user store, `ApplicationUserStore` (`Staffora.Data/ApplicationUserStore.cs`, registered by `AddApplicationStores()` in the app and the tests), opens a system-scope lease named with its reason for each of those lookups and closes it when the lookup returns.

It saves users under a lease too, since its context has no runtime tenant, and names who wrote: the circuit's effective user when they belong to the saved user's tenant, otherwise the tenant's system account.

A new user without a named creator is created by that writer, and every update is named as edited by it for that save, which is how sign-in counters, password and security-stamp changes are recorded: the system account's before any session, the user's own or their administrator's within one. A user created as the circuit's impersonated user also records the impersonating platform owner as `ImpersonatedById`.

Since its saves run under a lease, the store itself keeps them in the session's tenant: while the circuit has a user, a user of another tenant than the circuit's effective one is neither created, updated nor deleted, unless the circuit has platform reach (the console, writing on that tenant's behalf); with no user in the circuit, as when signing in, it writes any tenant's user.

A lookup by address that finds two users finds nobody, rather than failing. Signing in also reads the user's tenant's state (`FindTenantStateAsync`), under the same kind of lease, to refuse a tenant that is not Active. The store's `Users` query, and the users of a role or a claim, stay filtered and read nobody.

The session's first read of the signed-in user (`UserSessionService`) and the impersonation authorizer's read of a platform owner and a target user of any tenant (`ImpersonationAuthorizer`) are the only other leases of this kind; every service reads users through the filter, or through the platform lease on the console.

**System accounts.** Every tenant has exactly one system account (PRODUCT.md, Actors): the user that rows written on the tenant's behalf are stamped with, so a user of another tenant never lands on them (`Staffora.Core/Entities/Identity/SystemAccount.cs`).

- Its id is the one id not generated by EF: a name-based UUID, version 5 (RFC 9562), of the tenant id's 16 big-endian bytes hashed with SHA-1 under the fixed namespace `SystemAccount.IdNamespace`, so stamping needs no lookup and the same tenant always gets the same id. It never collides with an ordinary user's id, which EF or `Guid.NewGuid` generate with version 4.
- Its user name is `system:` (`SystemAccount.UserNamePrefix`) and the tenant id. Identity's default user validator refuses the colon, and `UserService` refuses any user name starting with `system:` when it creates or renames a user, whatever characters the validator allows; a rename runs Identity's user validators and updates the normalized user name and address. It is written with no password, email or role. It is Active, and the user workflow never moves it (each step's condition refuses a system account).
- `UserService` builds each new user itself (`CreateApplicationUserAsync` from the dialog, `CreateUserAsync` with a chosen password, both through the user workflow's create step), copying only the name, user name, address, phone number and custom field values from the caller, so a new user always gets a fresh version-4 id and never the system-account flag.
- `SystemAccountService` (`Staffora.Data/SystemAccountService.cs`) ensures it, idempotently, writing it directly rather than through Identity: the seeder and the test scenarios for every tenant they create, app startup for every existing tenant (`EnsureForEveryTenantAsync`), and tenant onboarding.

  It accepts the row holding the derived id only while that row is exactly what it writes (flagged, of the tenant, the account's user name, no password, no address); anything else, an ordinary user holding the id included, is refused and logged with the tenant id. At startup each tenant is ensured on its own: one that fails is logged and reported in the summary, the others are still ensured and the app starts.

  The failing tenant stays fail closed, since a row stamped with an account that is missing or not its own is refused by `SaveChanges`.
- It never signs in: `ApplicationSignInManager` (`Staffora.Services/Authorization/`) answers no in `CanSignInAsync`, refuses to issue its cookie and fails the security-stamp check of any cookie naming it (Identity's cookie revalidation and the circuit's revalidating state both use it), whether or not it has a password; the session gate opens no session for it. It holds no role: `RoleHoldingService.AssignUserToRoleAsync` refuses it. The impersonation authorizer (`ImpersonationAuthorizer`) refuses it as a target, at start and on every circuit and revalidation whose cookie names it.
- User lists, counts and pickers leave it out with `ExceptSystemAccounts()`, not a query filter, so a row it stamped still loads its creator; `UserService` reads, edits and resets the password of no system account.
- None of this stops a direct write to the users table. A flagged user passes as a stamped creator or editor only under the id derived for the row's tenant, so a row flagged by hand under another id is refused.

### ImpersonationAudit

One impersonation session ([ADR 0014](adr/0014-session-on-the-auth-cookie-audited-impersonation.md)), a platform table: no `TenantId` and no `ITenantEntity`, since every row crosses the tenant boundary and no tenant may read it (`Staffora.Core/Entities/Platform/ImpersonationAudit.cs`).

- `ImpersonatorId` → ApplicationUser (the platform owner who acted), `TargetUserId` → ApplicationUser, `TargetTenantId` → Tenant (the target's tenant at the start); all NoAction, so the trail keeps every user and tenant it names
- `Started` (UTC), `Ended` (UTC, null while the session runs and for a session that lapsed through a sign-out or a closed browser)
- Shown and written only in system scope, and append-only there: inserted, then closed once by giving its empty `Ended` a value with nothing else changed; never otherwise updated, never deleted, and never the target of `ExecuteUpdate` or `ExecuteDelete` (see [Tenant isolation](tenant-isolation.md))
- Written by `ImpersonationAuditWriter` (`Staffora.Services/Authorization/`), which records a start and returns the row's id, which the auth cookie then carries; a switch closes the cookie's own row in the same save, and an end closes the cookie's own row, writing nothing when it is already closed. Rows are addressed by id because a platform owner may impersonate in several browsers at once (tabs of one browser share its cookie). A circuit applies a cookie's impersonation only while its row is open and records exactly that owner and target (`IsOpenAsync`)

### ErrorLog

One error the application logged, a platform table: no `ITenantEntity` and no foreign keys, so an error is recorded whatever ids it names and never keeps a user or tenant from being removed (`Staffora.Core/Entities/Platform/ErrorLog.cs`).

- `Occurred` (UTC), `Level` (`ErrorLogLevel`: `Warning = 3`, `Error = 4`, `Critical = 5`, the values of `LogLevel`; Warning only for the writer's row saying how many entries the full queue dropped), `Category` (max 256), `EventId`, `EventName` (max 256)
- `Message` (max 4000) and `ExceptionType` (max 512); `ExceptionDetail`, the exception's text with its inner exceptions and stack traces, unbounded in the column and capped at 32,000 characters by the writer (on the model test's short allow-list). Message and exception text have anything that looks like a secret replaced (`SecretScrubber`)
- `CorrelationId` (max 64), `RequestPath` (max 512, the path without its query string), `TenantId`, `UserId` (the effective user) and `ImpersonatorId`: labels from the log scope the entry was written in, without foreign keys
- Shown and written only in system scope, never updated (see [Tenant isolation](tenant-isolation.md)); read by the platform owner through `PlatformConsoleService.QueryErrorLogAsync` on the platform console's `/superadmin/errorlog`
- Written by `ErrorLogWriter` (`Staffora.Services/Diagnostics/`) from a bounded queue that the logging provider fills; see [Error log and log scopes](features/operations.md#error-log-and-log-scopes). The retention pass removes rows older than `Retention:ErrorLogDays` (90 days) in batches ([Retention](features/operations.md#retention))

### ApplicationRole

`IdentityRole<Guid>`. Only `Admin` (`AppRoles.Admin`, the SuperAdmin role) is persisted, by `DatabaseSeeder` in every environment and by the platform bootstrap. `AppRoles.StandardUser` is an in-memory fallback that `UserSessionService` assigns when a user has no Identity role.

## Entity attributes

Custom fields per entity type and tenant, without schema changes. Each supported entity type gets its own definition table and value table.

- **Definition** (`EntityAttributeDefinitionBase<TEntity>`, non-generic `IEntityAttributeDefinition`):
  - `Id` (`Guid`), `Name` (max 100);
  - `ValueType` (`AttributeValueType`, an int: Integer 0, Number 1, Date 2, Text 3, Boolean 4, Choice 6; 5 is reserved and never reused);
  - `IsRequired` (`bit`, default 0): the field must be filled before its entity takes a step its workflow guards with `RequiredAttributesCondition`, and stays filled in the state that step leads to; never on a yes-or-no field (`AttributeDefinitionRules`);
  - `Options`: a choice's options as JSON, `nvarchar(max)` bounded by the rules (at most 50 options, each a key of at most 40 characters, a label of at most 100 and a retired flag);
  - `TenantId` (`Guid?`; null = global; a foreign key to `Tenants`, `NoAction`, never changed after insert);
  - the audit columns `Created`, `CreatedById`, `Modified`, `ModifiedById`, `ImpersonatedById` with `NoAction` foreign keys to the users who wrote the row, stamped in `SaveChanges`;
  - `RowVersion` (`rowversion`, a concurrency token): an update over a field someone else saved since it was read is refused, never last-save-wins; a step's transition lock moves it too, so the step reads it again under its lock.

  A definition is a state entity ([ADR 0033](adr/0033-custom-fields-have-a-lifecycle.md), `StateEntityBase<CustomFieldState>`): `State` (`CustomFieldState`, an int: Create -1, never stored; Draft 0, the default; Active 1; Inactive 2) and `IsInTransition`, both concurrency tokens, written only by its workflow, which has no delete; only an Active field reaches a tenant's dialogs, lists and required rules.

  Its history (`StateHistoryEntry`) is its tenant's, stamped with the tenant's system account, or for a global field the platform tenant's. Definitions are not `ITenantEntity`; they get their own filter and write checks (see [Tenant isolation](tenant-isolation.md)).

  A name is unique per scope: among one tenant's fields of an entity and among the global ones (`IX_{Table}_TenantId_Name`); a tenant's field never takes a global field's name nor the reverse, which the service judges across the two scopes.
- **Value** (`EntityAttributeBase<TEntity, TDefinition>`, non-generic `IEntityAttributeValue`): key `(EntityId, EntityAttributeDefinitionId)`, typed nullable columns `StringValue` (max 4000, also a choice's option key), `Int32Value`, `DoubleValue`, `BooleanValue`, `DateValue` (`date`).

  Only the column of the field's type holds a value, and a row always holds one: a cleared field has no row (the services delete it; `SaveChanges` refuses a row with every column empty or a text of white space alone). The foreign key to the owner cascades (a value is an owned row of its user or unit, without a lifecycle).

  On a state entity the value collection is a field of its workflow's `Attributes` area in every state (registration refuses a workflow that leaves it out), so `SaveChanges` judges every insert, update and delete of a value against the owner's persisted state (an unchanged value passes; a value inserted with its owner outside system scope by the state it is inserted in), as any declared child collection is.

  The one to the field is `NoAction`, and a field is never deleted (ADR 0033), so its values stay with their owners whatever the field's state. A value of a field that is not Active is never added or changed (`SaveChanges` refuses it, `AttributeValueRules.FieldNotInUse`); the one an inactive field holds is kept as it is.
- **Rules in the data context** (`Staffora.Data/ApplicationDbContext.CustomFields.cs`): every added or changed definition passes `AttributeDefinitionRules` against its stored row (a saved field keeps its type and every saved option with its key), and every added or changed value passes `AttributeValueRules` against its field (a retired option only where the stored row holds it) and holds something; a refusal is a `CustomFieldException` with the rule's reason.

  What they are and how the services use them: [Entity attributes](features/custom-fields-and-settings.md#entity-attributes-dynamic-custom-fields).
- Shared configuration: the extension methods `ConfigureAttributeDefinition<TEntity, TDefinition>()` and `ConfigureEntityAttribute<TEntity, TDefinition, TAttribute>()` in `Staffora.Data/Configurations/EntityAttributes/`.

### SlotAssignment

One staff member asked for or assigned to one slot ([ADR 0006](adr/0006-course-staffing-domain.md)). `TenantStateEntityBase<SlotAssignmentState>` and `ICommentedEntity`, decorated with `[SlotAssignmentWorkflow]`; shown in its own dialog (`SlotAssignmentDialog`, token `assignment`), opened from its slot's Staff view and from every notice about it ([Assignments](features/jobs-and-staffing.md#assignments)).

- `JobSlotId` → JobSlot (NoAction: an assignment is a state entity, canceled with its slot through its own workflow; it moves only within its slot group, as a step into Assigned takes an open slot of the group, `TakeOpenSlot`, inside its transition save scope), `ResourceId` → Resource (NoAction: a staff record is never deleted; never changed once saved). The job is the slot's.
- `RequestRoundId` → RequestRound (nullable, NoAction, indexed; never changed once saved): the round that sent the request.
- `RespondBy` (`datetime2`, UTC, nullable, [ADR 0041](adr/0041-a-request-expires-by-a-system-step.md)): the instant a request must be answered by, set by its create step and never changed: the tenant's "Time to answer a request" after sending (48 hours by default) or the time the coordinator chose, a round's requests carrying the round's; none on a straight assignment (`AssignAsksNoAnswerReason`) or when the tenant has no deadline.

  The request step refuses one already passed (`RespondByAheadReason`) and a round's request whose time is not the round's (`RoundTimeReason`).

  Once it passes, the job clock takes a Requested or StaffQuestion request into Expired (`assignment-expire`, `assignment-expire-question`, system-driven; `AssignmentExpired` to the job's coordinator and its sender, none to the staff member); Expired is not live, and a slot's or a round's cancellation leaves it alone.
- `State` (`SlotAssignmentState`: Create 0, Requested 1, Accepted 2, Declined 3, Assigned 4, NotSelected 5, Canceled 6, StaffQuestion 7, Expired 8) and `IsInTransition`. StaffQuestion ("Question to the coordinator", [ADR 0037](adr/0037-request-questions-are-workflow-steps.md)) is Requested with the coordinators' turn attached: an open request wherever Requested is read (`SlotAssignmentWorkflowAttribute.IsAsked`).

  Create is the entry state only: an assignment is inserted in it and moved by its first step in the same transaction, so no stored row stays there, and a row written without naming a state holds and asks nothing. Live: Requested, StaffQuestion, Accepted, Assigned. Holding (coverage, and the staff member booked in the availability): Accepted, Assigned.
- **Lifecycle** (`SlotAssignmentWorkflowAttribute`), every step taking no edits (nothing of an assignment is edited) and needing a session inside its own tenant:
  - Create → Requested (request, `PerformCoordination`) and Create → Assigned (assign, `PerformCoordination`), the creates;
  - Requested → Accepted (accept), Requested → Declined (decline, with a reason) and Accepted → Declined (take back a yes, with a reason), each `RespondToAssignment` and only by the assignment's own staff member (the owner rule, `OwnReason`: the step's effective user is the staff record's user);
  - Accepted → Assigned (pick, `PerformCoordination`);
  - Requested → NotSelected and Accepted → NotSelected (system-driven: no permission, never a button), taken when the slot group is full;
  - Requested, Accepted, Assigned → Canceled (withdraw request, cancel, cancel assignment; `PerformCoordination`, confirmed), also cascaded from a canceled slot.

  Requested, StaffQuestion, Accepted and Assigned → Canceled a second way too ([ADR 0044](adr/0044-taking-off-for-absence-and-open-again.md)), "Take off for absence" (`assignment-take-off-request`, `-question`, `-accepted`, `assignment-take-off`; `PerformCoordination`, offered only while an absence of the staff member blocks a remaining time of the job, `AwayReason`), which no cascade takes (`Transition.NeverCascaded`); its key in the history is what marks the slot open again, so no column records it.
- **Rules.** A request, an assignment, a yes and a pick need the job being staffed (`JobRules.StaffingOpen`: Coordinating, Confirmed, InProgress), the slot active and the staff member in service (`StaffServiceRules`); a no, taking back a yes and every cancel need the job staffed too, so nothing is rewritten once it is completed or canceled, and the job clock closes the Requested, StaffQuestion and Accepted ones as NotSelected, without a notice, as it completes the job; one Assigned assignment per slot (`OneHolderReason`; a held slot takes no request and no yes either) and one live assignment per staff member and slot (`OneLiveReason`).

  The four also need the staff member free for the job's remaining occurrences (`StaffFreeReason`: not absent, not out of service and not booked, Assigned or Accepted, on another job or another slot of the same job at the same time; any blocked occurrence refuses, with its dates), read by the assignment's guard (`SlotAssignmentGuard`, an `IStepPreparation`, for a create through `PrepareNewAsync`) on the step's context under the job lock, by the one availability rule ([Staffing dialog](features/jobs-and-staffing.md#staffing-dialog)).

  Qualifications are not judged (a mismatch is a warning).
- **Questions** (ADR 0037).

  - Requested → StaffQuestion (write a question) and StaffQuestion → StaffQuestion (write another question): `RespondToAssignment` and the owner rule.
  - StaffQuestion → Requested (answer the staff member, which hands the request back, or mark as handled, `assignment-question-handled`, without words, ADR 0038): `PerformCoordination` and never on one's own request (`NotOwnQuestionReason`).
  - Accepted → Accepted and Assigned → Assigned (mark as handled, `assignment-accepted-message-handled`, `assignment-assigned-message-handled`, ADR 0038): only while the staff member's last message waits for a reply, same gate.
  - StaffQuestion → Accepted (`assignment-accept-question`) and → Declined (`assignment-decline-question`), as from Requested.
  - StaffQuestion → Canceled (`assignment-cancel-question`, the one cascade target of a slot's cancellation and a round's close) and → NotSelected (`assignment-close-question`, system-driven).

  Every question step needs the job staffed and writes its required prompt's words into the staff thread. The state is stored as its number and no check constraint names the states. The filtered index `IX_SlotAssignments_OneLivePerStaff` still names Requested, Accepted and Assigned only: the one-live rule counts StaffQuestion under the job lock, and widening the index's filter needs a migration ([KI-70](known-issues.md)).
- **Thread.** Its one comment thread is the staff conversation (`CommentAudience.Staff`): a decline's or a withdrawal's reason is written there by the step, and while the request is open (Requested, StaffQuestion) only the question steps write in it (ADR 0037); the staff member reads and posts in it on their own assignment (`ViewOwnAssignments`, `RespondToAssignment`), the coordinators with `ViewCoordination` and `PerformCoordination`.
- **Whose turn** (ADR 0010).

  `LastStaffCommentAt`, `LastCoordinatorCommentAt` and `StaffSeenAt` (`datetime2`, UTC, nullable) are the staff thread's bookkeeping. They are written by one-statement updates of the comment service's post (the poster's side, as its transaction's first statement, a millisecond after the other side's stamp when the clock has not passed it, and a coordinator's also after `StaffSeenAt`) and of the staff member's own read (`StaffConversationService`, allow-listed by `DataContextScanTests`).

  One step writes them too: a coordinator's "Mark as handled" on a yes or an assignment (ADR 0038) stamps `LastCoordinatorCommentAt` after the staff member's last message, and `StaffSeenAt` with it unless a real reply is still unseen, inside its transition save scope. No state opens them, the dialog's updater excludes them and they bear on no version check.

  `StaffConversation` judges them: the staff member wrote last (awaits a coordinator's reply), a coordinator wrote after the staff member last read (an unseen reply).
- **One writer at a time per tenant.** Every assignment step takes the tenant's job lock, under which the one-holder and one-live rules read the slot's assignments; two filtered unique indexes hold both rules whoever writes.
- **Slot groups**. The rules are judged per slot group (a group of one is a single slot): a request, an assignment, a yes and a pick need an open slot in the group (`GroupOpenReason`, alias `OneHolderReason`), and a staff member has one live row per group (`OneLiveReason`); the step into Assigned (assign, pick, claim) keeps its own slot when open, else takes the group's first open one.

  Entering Assigned does not cascade: `SlotGroupFollowUp` (an `IStepFollowUp`) closes the group's other live rows as NotSelected through the system steps once the group is full, correlated with the step that filled it, each with its notice; a slot's cancel or save that leaves a group of its job full settles it the same way (`SlotStepsSettleTheirGroups`).

  The per-slot indexes (`IX_SlotAssignments_OneHolder`, `IX_SlotAssignments_OneLivePerStaff`) are unchanged and stand behind it.
- **Request rounds**. A request tied to a round is created only while the round is open and for its anchor (`RoundOpenReason`), and told with `AssignmentRequestedInRound` (with the round's rule) instead of `AssignmentRequested`.

  Accepted → Assigned (`assignment-claim`, system-driven): a yes to an open first-to-accept round takes a slot at once in the yes's transaction (`SlotGroupFollowUp`), telling the staff member (`AssignmentAssigned`) and the coordinators (`AssignmentTaken`); such a yes sends no `AssignmentAccepted`. A yes arriving after the group filled finds its request NotSelected and is answered `SlotAssignmentService.TakenBeforeYourYes`.

### RequestRound

Several staff members asked at once for one slot group (ADR 0027). `TenantStateEntityBase<RequestRoundState>`, decorated with `[RequestRoundWorkflow]`; shown in its own dialog (`RequestRoundDialog`, token `round`), opened from the slot dialog's Request rounds view and the filled notice.

- `JobSlotId` → JobSlot (NoAction, never changed once saved, indexed `(JobSlotId, State)`): the anchor, the group's representative as the round was sent; its group is the anchor's, derived on every read.
- `FirstToAccept` (bit): each yes takes an open slot at once (on) or waits for the coordinator's pick (off).
- `RespondBy` (`datetime2`, UTC, nullable): the instant its requests must be answered by, set when it is sent (the tenant's "Time to answer a request" or the coordinator's choice) and carried by each request; none means no deadline. Indexed `(TenantId, State, RespondBy)` filtered to rows that have one (`IX_RequestRounds_RespondBy`).
- `Requests`: the `SlotAssignment` rows with its `RequestRoundId`.
- `State` (`RequestRoundState`: Create 0, Open 1, Filled 2, Closed 3, Expired 4) and `IsInTransition`.

  **Lifecycle** (`RequestRoundWorkflowAttribute`), every field read-only, every step taking no edits inside its own tenant: Create → Open (`round-send`, `PerformCoordination`: the job staffing-open, the anchor active, the group open), sent in one transaction with its requests (`RequestRoundService.SendRoundAsync`, 1 to 30 staff members; a refused request refuses the round); Open → Closed (`round-close`, `PerformCoordination`, confirmed; Closed cascades into each Requested request's `assignment-cancel-request`, leaving yeses, holders and closed requests); Open → Filled (`round-filled`, system-driven, run by `SlotGroupFollowUp` once the group is full; `RoundFilled` to its sender).

  Open → Expired (`round-expire`, system-driven, run by the job clock once `RespondBy` passed while a request is unanswered; Expired cascades into each unanswered request's expire step, leaving answered ones, and sends `RoundExpired` to its sender and the job's coordinator; [ADR 0041](adr/0041-a-request-expires-by-a-system-step.md)). Closed leaves expired requests alone too. Every round step takes the tenant's job lock.

## Design notes

| Rule | Reason |
|---|---|
| `Guid` keys everywhere | No sequential ids leaking across tenants, and one key type for every entity, state entities included. |
| Tenant = company | A tenant is one company using the platform, with one organization tree under its `Company` root. The businesses that order staff are customers, not tenants of their own unless they get a portal. |
| Users are tenant rows | Every user, platform owners included, belongs to exactly one tenant (platform owners to the platform tenant), so `ApplicationUser.TenantId` is required and users are filtered like any tenant row (ADR 0012, ADR 0013). Identity finds a user before any tenant is known only through its user store's own leases. |
| One organization tree per tenant | A staffing company is one business: one root, one parent per unit, roles granted tenant-wide (ADR 0021). |
| One table pair per attribute-enabled entity | Focused queries and real FKs, instead of one polymorphic table. |
| Explicit `OnDelete(DeleteBehavior.NoAction)` on every relationship | EF defaults required FKs to Cascade; this codebase opts out everywhere except owned rows without a lifecycle (`TenantRolePermission`, attribute values from their owner but never from their field, segments, timetable slots, a slot's and a service's qualification rows, an order's lines, and ASP.NET Identity's own user and role rows), proven by a model test (ADR 0022). |
| Audit columns on every tenant row | `Created`/`CreatedById` and `Modified`/`ModifiedById` say who made and who last changed a row; the workflow history records transitions (ADR 0022). |

## Migrations

`Staffora.Data/Migrations/`. Until the first shared deployment the migrations are a single `InitialCreate`, regenerated whenever the model changes; from the first shared deployment on they are additive only (ADR 0022).

A design-time factory (`Staffora.Data/DesignTimeApplicationDbContextFactory.cs`) builds the context from the same options method as the app and the tests (`ApplicationDbContextOptions`, which also gives contexts built outside the app the ASP.NET Identity schema version the app configures, so every caller sees the same model), so `dotnet ef ... --project Staffora.Data` runs without the web project; it connects to `-- --connection "<connection string>"` when given, else to `ConnectionStrings__DefaultConnection`, else to the local development database.

The folder holds one `InitialCreate`; `dotnet ef migrations has-pending-model-changes` must report none before a change is done, and a unit test (`ContextOptionsTests`) checks the same without a database.

The app applies pending migrations at startup and seeds on a system context inside a system-scope lease, with production data (the `Admin` role, and nothing with credentials) separate from Development data (the platform tenant with its seeded owner; seeded credentials exist only in Development).

In Development, startup then builds the demo tenants through the services, as that owner and the people it onboards, never as rows of the seeder (`DemoDataSeeder`, [Demo data](features/demo-data.md#demo-data)). Outside Development the platform tenant and its first owner come from the one-time bootstrap (`Staffora.Data/Seed/PlatformBootstrap.cs`, see [First platform owner](authentication.md#first-platform-owner)).

Each seeding step looks for what it would add first, and the demo builds only the demo tenants no tenant is named after yet, so a second start changes nothing (`DatabaseSeederTests`, `DemoDataTests`).

With `STAFFORA_E2E_SKIP_STARTUP_SEED` set to `1` or `true` a Development start leaves seeding out, the demo included (migrations and system accounts still run): the end-to-end server sets it, since its database is seeded by `Staffora.E2ESetup` through the same services (`Staffora.Test/E2E/README.md`). Any other environment logs the setting and seeds as usual. Commands are in the [README](../README.md).
