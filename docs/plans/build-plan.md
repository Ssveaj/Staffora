## How to work this plan

- Take steps in order, one at a time. Step ids are stable; a letter suffix (2.2a) marks a step inserted after the plan was first numbered.
- A step is done only when the **Definition of done** in `.github/copilot-instructions.md` holds: build, fast tests, database tests and journeys as the change requires, every **Done when** clause proven by a named test, then tick the step and close its known issues in the same change. Report the commands you ran and their results.
- New behaviour gets a test at the lowest level that proves it, in the folder ADR 0018 names for that level.
- Work outside this plan (a feature after phase 7, or an item from Later) gets its own `docs/plans/<feature>.md` with the sections Why, Decisions (D1, D2, …; a lasting one becomes an ADR), Out of scope, Phases (steps with **Done when**, as here) and Open points. The Definition of done applies unchanged; when the feature ships, its plan is deleted and what remains true moves to the docs.
- Every entity with a lifecycle is a state entity with a workflow attribute, shown only in a StateEntityDialog with transition buttons, and its custom fields sit in the workflow's `Attributes` area (ADR 0009). The `workflow-state-entities` skill holds the recipe; reuse its shared pieces instead of writing new ones.
- A step that introduces a new actor (system owner, coordinator, staff member, orderer) also adds that actor's persona to the end-to-end preparation (2.9).
- Each known issue is closed by exactly one step; a step that closes only part of one says which part. When ticking a step, rewrite "closes KI-nn" for each deleted entry as plain words ("closed the Core build failure"), because the docs tests require every KI reference to exist.

## Defaults for open domain questions

Defaults chosen so work could start; each is the behaviour the product was built with.

| Question | Default |
|---|---|
| Several slots per job, partial staffing | Yes; coverage shows partial |
| Job timetable | Weekly `JobTimeSlot` rows (weekday, start, end) across the period; used for conflicts and pattern fit |
| Staff member withdraws a yes | Allowed until the coordinator picks (Accepted → Declined) |
| Confirm step | `Coordinating → Confirmed` by coordinator, not guarded on coverage |
| Who registers vs coordinates | `JobsCreate` registers; `PerformCoordination` starts and confirms |
| Job coordinator | `Job.CoordinatorUserId` is set by the transition into Coordinating and receives the customer-thread notices |
| Re-staffing a running job | Assignments may be requested or made while the job is Coordinating, Confirmed or InProgress |
| Qualification mismatch | Warning in the candidate list, not a hard block |
| Candidate ranking | Staff holding every required qualification first, then by number of matching qualifications, then fewest held jobs in the period, then name |
| Candidate unit scope | A unit in the question covers the units in use below it: staffing a unit considers the staff members of its teams (`CandidateRules.UnitsInScope`, since plan step 5.2) |
| What books a staff member | Assigned and Accepted block the timetable slots; an open request (Requested) is a warning |
| Outside the staff member's work pattern | Warning, not a block |
| Availability in v1 | Work pattern plus absence, and closed days since plan step 9.4 |
| Absence types | Planned leave needs coordinator approval and blocks once approved; sick leave blocks on report; the staff member and the approvers read the reason, and either side may ask the other a question through a step (ADR 0035) |
| What coordinators register on a staff member's behalf | Absence |
| Staff without a login | No; every resource is a user |
| Resource deactivated with future assignments | Assignments stay and the job shows as needing re-staffing |
| Who may give the Staff role | Holders of `RolesEdit`; the grant ceiling exempts the `Personal` area |
| Notice recipients | A named user, or holders of a named permission in the tenant |
| User lifecycle | Create, Active, Inactive; invitation flow later |
| Coordinator scope | Per tenant; roles are held on a unit and grant tenant-wide (ADR 0021) |
| Cancellation | `CanceledByCustomer` / `CanceledBySupplier`; reason as transition comment |
| Customer approval of a confirmed job | None; confirmation by the coordinator is final |
| One customer, several suppliers | No; a portal customer is managed by one supplier |
| Portal job's unit | The customer's `DefaultUnitId`, set when the portal is enabled |
| Staff member talks to the customer directly | No; the coordinator relays (ADR 0010) |
| Thread closes | For a staff member when the request is no longer live; for everyone when the job is Completed or canceled |
| Edit or delete comments | Neither |
| Customer writes in the thread | Attention marker plus a notice to the job's coordinator |
| Notification channels in v1 | In-app only; e-mail later |
| Notification retention | A read copy goes 180 days after it was read, and its notice once no copy is left (plan step 9.5) |
| Tenant states | Only platform owners change them; Pending deletion and Archived refuse all access; a tenant in Pending deletion for 30 days is purged and archived, keeping only its tenant row (plan step 9.5) |
| Impersonating into a tenant in Setup | Only its system owner |
| Impersonation reach | Any tenant, no depth limit; starting a new impersonation switches target and closes the previous session |
| Deleting an organization unit | Only a leaf unit nothing uses; never the `Company` root; archiving needs every unit below archived first |
| Unit names | Unique among siblings (tenant, parent, name) |
| Link-row keys | Composite key of the two foreign keys plus `TenantId`; no separate `Id` |
| Owned child rows (`WorkPatternSegment`, `JobTimeSlot`) | Tenant rows like every other (`TenantId`, filtered), cascading with their owner |
| Row audit | `Created`/`CreatedById` and `Modified`/`ModifiedById` on every tenant row; field-level history not kept |
| First owner's password | The platform owner (or a CustomerAdmin for orderers) sets an initial password, shown once; invitations come later |
| Hard delete vs terminal state | Hard delete only in entry or draft states, or Inactive with nothing depending on the entity; otherwise Archived, Inactive or Canceled |
