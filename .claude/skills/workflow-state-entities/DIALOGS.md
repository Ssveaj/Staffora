# StateEntityDialog

Every state entity is shown in a StateEntityDialog: a shared host draws the header, body, footer and transition buttons; each entity supplies only a **context**, a **body** component and an **opener**. User-facing behaviour of dialogs (focus, Esc, sizes, the form dialogs) is described in [docs/features/lists-and-dialogs.md](../../../docs/features/lists-and-dialogs.md#dialogs); this file is the build recipe and the rules the scans enforce.

Shared pieces live in `Staffora.Blazor/Components/Common/Dialogs/StateEntity/` (host, layout, header, footer, transition button, context bases, routing) and `Components/Common/WorkflowFields/` (the `StateField*` inputs). The test-only `TestParentDialog` (`Staffora.Test/Web/StateEntity/`: body, context, service, `TestParentWorkflowQueries`) is the worked example; `StateEntityDialogTests` shows every behaviour below on it.

## Recipe

1. **Workflow first.** States, transitions with descriptions, a save self-transition marked `IsSave` per editable state, delete into a `[DeleteState]`, field access per state ([SKILL.md](SKILL.md#adding-a-state-entity)).
2. **Context.** Subclass `StateEntityDialogContextBase<TState, TEntity>` with a constructor that takes the entity's service and the id and passes `{Entity}WorkflowQueries.WithWorkflowGraph` (a method group) to the base as the `QueryConfigurator`: the same graph the service's load uses. `EntityId` is a `Guid?`: null is create mode; it is set once. Declare the token with `[DialogRoute(DialogTokens.{Entity})]` (a new `DialogTokens` constant: 1 to 32 lowercase ASCII letters or digits starting with a letter, unique, never renamed). Override each part as **exactly one service call**:

   | Override | Service method | The service |
   |---|---|---|
   | `LoadUpdaterAsync(id, ct)` | `Load{Entity}UpdaterAsync(id, ct)` | Checks permission and tenant, loads with `WithWorkflowGraph()` plus display includes, returns `new DetachedEntityUpdater<T>(entity, context, options)` |
   | `SaveAndTransitionAsync(updater, transitionKey, comment, ct)` | `Update{Entity}AndTransitionAsync(updater, transitionKey, comment, ct)` | Checks the edit permission (the delete permission for a delete step when it owns the delete) and calls `WorkflowService.SaveAndTransitionAsync(updater, transitionKey, {Entity}WorkflowQueries.WithWorkflowGraph, comment, ct)` |
   | `NewEntityAsync(ct)` and `CreateEntityAsync(entity, transitionKey, ct)` (create mode only) | `Create{Entity}Async(entity, transitionKey, ct)` | Checks the create permission, builds a row of its own from the dialog's values (never passes the dialog's entity on) and calls `WorkflowService.CreateAndTransitionAsync(row, transitionKey, {Entity}WorkflowQueries.WithWorkflowGraph, ct)` |
   | `LoadHistoryAsync(id, query, ct)` | `Get{Entity}HistoryAsync(id, query, ct)` | Checks the permission its load checks and calls `StateHistoryService.GetHistoryAsync<{Entity}>` |
   | `LoadCustomFieldsAsync` | `Get{Entity}CustomFieldsAsync` | Entities with custom fields ([ATTRIBUTES.md](ATTRIBUTES.md)) |
   | `LoadEditorOptionsAsync` | `Get{Entity}EditorOptionsAsync` | Drop-down lookups and facts, read under the tenant filter; kept on the context's own properties |
   | `DeleteAsync(updater, key, comment)` (optional) | the service's delete path | When the service owns the delete, so a reader who may delete but not edit deletes from the footer |

   A result the user must read once (an initial password) goes to `ShowOnce(message)`, never into a log or the `DialogResult`. The opener sets `DefaultTitle`, `CreateTitle` and `EntityIcon` (a Material Symbols name).
3. **Body.** Implements `IStateEntityDialog<TContext>`. In `OnParametersSet`, once per entity version (`Context.Version` changed), it sets `Context.DisplayName` and, when it validates, `Context.OnBeforeTransition`. It binds `StateField*` components, `StateAreaFieldset` and `StateCustomFields` straight to `Context.Entity`, which is the updater's entity or the new entity in create mode. The body:
   - never decides a field's visibility, read-only or required state: it reads no state, no `IsInTransition`, no field config, and no sign of create mode (`IsCreate`, `EntityId`, `UrlSegment`, `Updater` or its snapshot, `HasSaved`, `DialogResult`, the titles, an entity's key or audit columns, an empty id);
   - uses only the edit channel of the context: `Entity`, `Version`, `Lifetime`, `DisplayName`, the footer's hooks, `NotifyEdited`, `NotifyChanged`, and the titles and icon the opener set;
   - writes no `Disabled`, `ReadOnly`, `Visible`, `disabled`, `readonly`, `required`, `hidden` or `aria-*` access attribute, no raw Radzen input or input element (nor one opened as a `DynamicComponent` or by a runtime type), no attribute, parameter or element name not written as one literal, no splatted attributes, and no `dynamic`;
   - contains no buttons, and calls no service in any lifecycle method (`OnInitialized*`, `OnParametersSet*`, `OnAfterRender*`), constructor, field initializer or render.

   `StateFieldScanTests` and `DialogArchitectureScanTests` hold these by reading the compiled body and everything it reaches (reflection is out of their reach and forbidden).

   **The edit channel.** The layout cascades the context and an `EditContext` over the entity and passes every field change on as `Context.NotifyEdited()`, so an input bound to the entity needs nothing. A body that changes the entity past an input (a child row added from code, a foreign key set from code) calls `Context.NotifyEdited()` itself; otherwise the header and footer show the entity as it was. An edit re-renders the header and footer and asks the server nothing.
4. **The edits and the step, one transaction.** The context does it; the body only checks.
   - Before a step that does not lead into a delete state, the context asks the body's optional `OnBeforeTransition(transition)` (false gives the step up and the body shows its own message). It may ask, in a form dialog through `OpenFormDialogAsync`, what a step needs beyond the entity's fields and hand the answer to the context for that one step (the customer's "Enable portal", `EnableCustomerPortalDialog`, `CustomerDialogContext.PortalRequest`).
   - The context then judges the step's conditions on the edited entity in memory (in create mode always, in edit mode when there are edits). This is instant feedback, not the decision. A condition that throws refuses with "This step cannot be checked yet."; a condition on a navigation the dialog does not hold as the server would (`DialogNavigationLoadState`) is left to the server. A condition that asks an `IStepPreparation` answers from what the footer's question read in the same circuit; a test page that opens such a dialog registers the preparation from the same scope as its `WorkflowService`.
   - A `TakesNoEdits` step never goes with edits: while the dialog holds edits its button stays greyed with `TransitionRefusals.PendingEdits` (`TransitionOffer.WaitsForSave`), and a click sends nothing (`AbsenceDialogsTests`). A step whose edits the user may not save (the edit-authority rule) waits the same way with `TransitionRefusals.EditsNotYours` or `NoEditsHere`; a delete is left alone (`JobDialogsTests`).
   - Create mode: `CreateEntityAsync` creates the row and runs the step in one call. Refused, nothing is stored and the dialog stays in create mode with its edits; done, the context takes the new id and loads the row's updater. The workflow service inserts a copy, so a refused create never changes the dialog's entity.
   - Edit mode: `SaveAndTransitionAsync(Updater, key, comment)` sends the updater, never the entity, and `WorkflowService.SaveAndTransitionAsync` does the rest in one transaction ([TRANSITION-ORCHESTRATION.md](TRANSITION-ORCHESTRATION.md#entry-points)). Any refusal rolls the edits back with the step; the footer shows the server's reason and the edits stay in the form. Once committed, the context reloads and replaces the updater.
   - A step into a delete state skips the in-memory check and the edits: it runs on the stored row through `DeleteAsync`, by default `WorkflowService.TransitionEntityAsync` with the graph.
   - A step whose updater no longer names the opened row is refused.
5. **Opener.** Exactly one id-only opener per body, of this shape (the registry finds it, a list row calls it, a link reopens through it):

   ```csharp
   public static Task<StateEntityDialogResult> OpenAsync(DialogService dialogService, {Entity}Service service, Guid id, StateEntityDialogOptions? options = null)
   ```

   `TService` is the entity's concrete service class as registered, never an interface or abstract class. Optionally `OpenCreateAsync(DialogService, service, seed…)`. Both build the context and call `dialogService.OpenStateEntityDialogAsync<TBody, TContext>(context, options)`, the only door (`DialogUsageScanTests`), handing the options on untouched (or changed only with `with`). It answers a `StateEntityDialogResult` (`Changed`, `Deleted`, `EntityId`). A session opener builds `new StateEntityDialogSession([StateEntityDialogTarget.For<TBody, TContext>(context), …], start)` and calls `OpenStateEntityDialogSessionAsync(session)`. Every body opened either way is covered by the accessibility sweep or excepted with its reason (`AccessibilitySweepCoverageTests`).
6. **Lists and child collections.** A list row on `ListView` opens the dialog through the opener, and the list reloads when it closes; the row carries no actions. A child collection is a view tab ([Views and sessions](#views-and-sessions)). One tab per thing; nothing is shown twice.
7. **Edit mode for complex dialogs.** A read view with an "Edit" self-step uses the step-wise before-hook and a `TransitionFilter` that offers only Save while editing; "Discard changes" lives in `FooterActions`.

## Loading

Decision: [ADR 0017](../../../docs/adr/0017-dialogs-load-through-one-service-call.md).

1. **Open.** The opener builds the context and calls the door. The host pushes the dialog's segment (`DialogToken` and the id) on the URL's dialog stack (`UrlStateService.PushDialog`; create mode pushes none until the first save). Dialog options: no title bar, Esc and the close button close through `CanClose` (never while a step runs, and with unsaved changes only after "Discard changes?"), no close on overlay click, no autofocus. Focus and Esc are handled by the host's module (`wwwroot/scripts/state-entity-dialog.js`); never add your own.
2. **Navigation.** One guard per circuit answers for every open dialog (the top dialog's `StateEntityDialogNavigationGuard`, registered through `OpenStateEntityDialogs`). While a step runs an internal navigation is held back; with unsaved changes in any dialog it asks once, and the answer holds for all.
3. **One load.** `Load{Entity}UpdaterAsync` is the one call for the entity. Beside it, on the first load only and together (`Task.WhenAll`): `LoadCustomFieldsAsync` and `LoadEditorOptionsAsync`, one call each; a refusal of either is "could not open" with its reason. A context whose options follow the entity rather than the opening says `ReadsEditorOptionsWithEveryLoad`. The views' permissions and the history access are checked once, beside the first load.
4. **Failure.** A failed load renders "could not open" with the service's reason (a plain one for an error), is logged and never throws into the circuit. A missing and a foreign id give the same reason. Closing the dialog cancels `Context.Lifetime`, the token every load and step runs under.
5. **Footer.** One batched call (`WorkflowService.GetAvailableTransitionsAsync` with the context's graph) per `EntityId` or `Context.Version` change, never per render. In create mode one call to `GetTransitionAccessAsync` keeps out the saves the user may not take. Every edit then re-judges the steps in memory (`OffersFor`) without a server call.
6. **On demand.** History loads when the state pill's card first opens; a view mounts and loads only when first selected; comment threads load with the entity.
7. **Reload.** After a transition, or a refused step that left no edits, the context's internal `ReloadEntityAsync` replaces the updater without the loader. The public `ReloadAsync()` (a closing child dialog's, or a body's) runs the leave rule first when the entity has edits, so they are saved or asked about, never overwritten; it reloads nothing once the dialog has ended.

**Rules.**

- One dialog per entity, one load method per entity, one include graph per entity; every state entity has exactly one context.
- The footer is the one place a state entity's steps run, its Delete included: no page or component outside a dialog context runs a step or calls a service's `Delete{Entity}Async` of a state entity (`LifecycleCallScanTests`). Removing a record without a lifecycle (a role holding) is no step.
- Nothing writes during a load: create rows through a transition or an explicit action, mark things read through a command after rendering.
- The opener takes ids, not lookups; the same id-only opener serves deep links. An opener that shows another view than the first passes `StateEntityDialogOptions.View`, and a page that opens dialogs that way declares `[DialogViewOnPage(token, view)]` so a link or F5 reopens on the same view (the first level of the chain only).
- A navigation read by a condition, an action or an ownership rule belongs in `WithWorkflowGraph()`, never in an inline include.
- `DialogArchitectureScanTests` reads the compiled assemblies and holds: every context's `QueryConfigurator` is the `WithWorkflowGraph` its service's load applies to the query that reads the entity; `SaveAndTransitionAsync` is one call to `Update{Entity}AndTransitionAsync`, which runs `WorkflowService.SaveAndTransitionAsync` once with that graph; `CreateEntityAsync` is one call to `Create{Entity}Async`, which builds its own row and runs `CreateAndTransitionAsync` once with that graph; `LoadHistoryAsync` is one call to its service; no body calls a service as it is built or rendered, however the call hides (a service is anything in Staffora.Services or Staffora.Data, EF Core, or an injected type other than Radzen's UI services, navigation, JS interop, logging and the clock).

## Views and sessions

A dialog shows one entity; its **views** are tabs over that entity, and a **session** shows several entities in one modal, one at a time.

1. **Declared by the context.** `DeclareViews()` returns the views: a `StateEntityDialogView(key, label)` with `Order`, `Icon`, `Permission` (the one its data's service checks; none when whoever may open the dialog reads it), `Area` (a workflow area), `When` (a predicate over what the context loaded, never calling a service) and `StoredOnly` (waits for the stored row); or a `StateEntityDialogListView<TRow>(key, label, definition, load)` whose `load` is one call to the entity's service (`(query, ct) => service.Query{Entity}{Rows}Async(EntityId!.Value, query, ct)`), or to a child service the entity's service exposes through a property when that service checks the view's permission itself (`service.Holdings.QueryApplicationUserRoleHoldingsAsync(…)`), never a forward on the entity's service that only checks again and hands on. A key is lowercase letters, digits and hyphens; a duplicate or malformed key throws.
2. **Offered** while the reader holds its permission (failing closed when it cannot be checked), its area is visible in the persisted state, and, for a list view or a `StoredOnly` view, the entity has a row. The first offered view by `Order` opens; the body decides none of this.
3. **Rendered.** With more than one view offered, the layout draws `StateEntityDialogTabStrip` (the WAI-ARIA tabs pattern with manual activation). The body wraps each view's content in a `StateEntityDialogViewPanel Key="…"`, rendered once first shown and then kept hidden; a panel naming an undeclared key throws.
4. **The leave rule.** A hop between views of the entity's own fields keeps the edits in the form. Before the dialog shows what the database holds instead (a hop to a list view, a session's move, the public reload) the edits are settled by the state's designated **save step** only ([TRANSITION-ORCHESTRATION.md](TRANSITION-ORCHESTRATION.md#the-save-step)): never another self-transition, a forward step or a create. It runs only when the footer's answer for this version offered it and its conditions pass in memory. When the server refuses it, or no save can take the edits, or the state designates none, the user is asked "Discard changes?" with the reason: **Keep editing** stays with the edits; **Discard changes** reloads and goes on. While a step runs or the question is open, tabs, moves and a second settle do nothing.
5. **A view's data.** A list view's rows load when the view is first shown, never as the dialog opens; leaving the view or closing the dialog cancels the load. A new entity version reads the shown view's rows again and marks hidden views stale. The load is one call to the entity's service (or its child service, held by the permission scan to a check naming the view's permission), so the service checks the permission and reads under the tenant filter whatever the tabs show (`DialogArchitectureScanTests`).
6. **Child lists and stacked dialogs.** `StateEntityDialogChildList<TItem>` keeps its query out of the address (`DialogScope`; one that must keep it there takes `AddressPrefix` and `BindAddress`). A row opens the child's own dialog on top through `OpenRow`. When the child closes having changed something, the parent reloads through `ReloadAsync()` (the leave rule first), then the list reads its page again and the focus returns to the row; a child that changed nothing reloads only the list. A form dialog of a row without a lifecycle answers `Changed` when it changed what the parent may do. A view's add action reloads the parent the same way, so its footer is judged again at once. A view component that acts in place (`SlotStaffingPanel`, `AbsenceImpactView`) takes the dialog's context, reads and acts through its own services, reloads the parent through `ReloadAsync()`, and is listed among the shared pieces of `StateFieldScanTests`.
7. **Sessions.** `StateEntityDialogSession` holds targets (one context each) and opens on one; a session of several takes saved rows only. A move (`GoToAsync`) runs the leave rule on the shown target, holds it busy and inert, loads the next one, and only then swaps it in (no loader). A target with edits is never reloaded. Navigation and close ask once about every target with edits. A deleted target is removed and its neighbour shown; the dialog closes only on the last. A session never swaps while another dialog is open above it.
8. **Scans.** `StateFieldScanTests` reads `StateEntityDialogViewPanel`, `StateEntityDialogChildList<>`, `StateEntityDialogSession` and `StateEntityDialogTarget` as shared foundation, and the body's own columns, keys and opener as body code. `DialogArchitectureScanTests` admits in a body only what loads nothing: a workflow graph named as a method group or from a configurator lambda, `DetachedEntityUpdater<T>.HasChanges`, and `StateEntityDialogContext.LoadState`; each declared list view's load is one call to the entity's service.

## Routes and restore

The address names the open dialogs (`?dlg=token-id.token-id`, outermost first; [docs/features/lists-and-dialogs.md](../../../docs/features/lists-and-dialogs.md#url-state)), and F5, a pasted link or a new tab reopens that chain.

1. **Declared on the context.** `[DialogRoute(DialogTokens.{Entity})]` names the dialog. `StateEntityDialogContext.DialogToken` reads it and nothing else, is not virtual, and throws for a context without one. The attribute is not inherited: every concrete context declares its own.
2. **Registered.** `DialogRouteRegistry` (built at startup, `AddDialogRoutes(typeof(Program).Assembly)`) maps each token to its context, its one closed body and that body's one id-only opener of the fixed shape. A context without a token, an invalid or duplicate token, a context without a body, and a body without the opener or with two stop the app (`DialogRouteException`; `DialogRouteRegistryTests`, `AppWiringTests`).
3. **Restored once per arrival.** `StateEntityDialogRestoreHost`, inside the session gate of both layouts, takes the chain with `UrlStateService.TakeArrivedDialogChain()` and reopens it only when the page's own `[Authorize]` policies let the session in; otherwise nothing opens and no service is asked. It reopens level by level through each token's opener, each loaded before it shows.
4. **Each level is authorized by its own load alone** (the tenant filter and the load's permission check, as a list row's open). A row the reader cannot see (another tenant's, deleted, refused, failing) opens nothing, not even "could not open", and the chain stops there; a missing and a foreign id read alike, so a link never reveals whether another tenant's row exists. What a link can reach is never more than its reader can open one dialog at a time.
5. **Read strictly.** `DialogStackSegment.TryParse` reads a segment in any case and keeps the form the app writes. An unknown token, a non-`Guid` id or a duplicate segment stops the chain with a warning; unparsable text, values over 512 characters and segments past the eighth are dropped. Nothing throws into the circuit. An opener that does not hand its options on stops the chain with a warning.
6. **Back and Forward.** Only the arrival reopens; Back or Forward inside the app shows the page without the dialogs.
7. **Create mode and sessions.** A dialog in create mode has no segment until its first step gives the row an id. A session's segment is the record it shows.
8. **Never secret.** The address holds tokens and row ids only; what a reader may see is decided by the load, under the tenant filter, every time.

## Header and history

[ADR 0036](../../../docs/adr/0036-history-is-for-owners-and-the-workflow-inspector-is-gone.md).

- The header shows the entity icon, the title, the **state pill** (display name, icon, `[StateStyling]` colour) and, for a reader who may read the history, a history button (`aria-label="History"`). The state colour fills the header; every text on it takes its colour from `DialogStateColors`. A body never sets colours on the frame; it reads `--dialog-state-color` if it needs the accent.
- The pill is a disclosure button that opens a card with the state's `[Description]`. For a reader who may read the history, the card also shows the last three steps and a "Full history" button (`StateHistoryDialog.OpenAsync`, through `OpenFormDialogAsync`). There is no workflow inspector: the footer is where a reader learns what the record can do next.
- **Only an owner reads the history:** an active system owner of the entity's tenant (`SystemOwners.IsActiveOwnerAsync`), or a platform owner on the platform console (platform reach, not impersonating). The context asks once (`LoadHistoryAccessAsync` → `StateHistoryService.MayReadHistoryAsync`; a failure answers no) and draws nothing of the history for anyone else. The server decides regardless: `StateHistoryService.GetHistoryAsync` refuses everyone but an owner with `StateHistoryService.OwnersOnly` before anything is read.
- **The read** is lazy (on the card's first opening, never as the dialog loads), per entity version, and guarded by a refresh token. `StateHistoryService.GetHistoryAsync<TEntity>` reads the entity under the tenant filter (foreign and missing ids alike), the entity's own tenant's entries only (also under the platform lease), keyset-paged (`StateHistoryQuery`, at most 50 per call), with times in the entity's tenant's zone (`TenantClock`).
- **Who.** A step names its actor only when they are a user of the entity's tenant (its system account reads "System account"); an actor from outside reads "Someone outside this organization" inside the tenant. Another tenant's names never appear.
- State chips take their fill from `[StateStyling]` and text from `ColorContrast.OnFill`, set inline as custom properties so the stylesheet holds no colour of its own (`TokenUsageScanTests`).

## Transition buttons

- **Candidates.** The footer takes the transitions from the current state ordered by `SortOrder`, drops `IsSystemDriven` ones, offers only the entry state's saves before the first save (its self-transitions, or, for a `Create` state without one, the steps out of it), withholds steps with a `CommentPrompt` until the row exists, applies the dialog's `TransitionFilter` (presentation only), then asks the server which the current user may run. A step the access gate refuses is never drawn.
- **Visibility.** A button renders only when its transition can run. With `ShowWhenBlocked` it renders greyed (`aria-disabled="true"`, never `disabled`, so it keeps the focus) with a card listing the failing conditions; a click does nothing. There is no hide flag: to hide a button, add a condition. As the user edits, steps appear, un-grey or grey at once with no server call. There is no next-step hint above the buttons: a greyed step's card says what it needs.
- **Edit mode** ([ADR 0031](../../../docs/adr/0031-dialogs-open-locked-until-edit.md)). A saved record opens locked when its state has a step that stores edits (`Workflow.GetEditAuthority`): every field is read-only (`IsUnlocked` false), and the footer draws its own **Edit** button (`data-dialog-action="edit"`) in that step's place for a reader the gate lets through. Edit unlocks the fields and leaves **Cancel** (`data-dialog-action="cancel"`) and that step; Cancel drops the edits and locks again; every load locks again. Edit and Cancel are the footer's own buttons: never declare an Edit step in a workflow. Only the machinery's test entities override `OpensLocked`. Tests press Edit before typing into a saved record (`DialogEditing.Edit()`).
- **Placement and order.** `Placement = Leading` sits far left (hand back, undo, new version); everything else sits right. `SortOrder` 10 for back steps, 20 for neutral (save, edit), 30 for forward, so the primary action is rightmost.
- **Look.** Label from `Transition.Label` (or the dialog's `TransitionLabel`; null shows the target state's name), icon from `Transition.Icon` or the target state's `[Icon]`, accent from the target state's `[StateStyling]`: a white button with a 3 px leading edge and its icon in that colour, text in the text colour.
- **Click sequence.** Confirmation (`ConfirmationMessage` through `ConfirmAsync`, destructive for a delete) or comment prompt (`CommentPrompt` through `PromptAsync`), never both; Cancel on either returns the focus to the step's button. Then busy (`Context.IsBusy`), the body's check, the edits with the step, and the result. A refusal is shown in the footer in the service's words; an unexpected exception is logged and shown as a plain message, never its text. Refusals name steps by their labels and permissions by their display names, never by keys.
- **One at a time.** While a step runs, a second click does nothing, the dialog does not close, navigation is held back and the body is inert.
- **After.** On a delete state the dialog closes (the result says `Deleted`); otherwise it reloads. The host closes by reference, so a dialog whose delete completes under another dialog closes once that one has. The refresh token discards answers for a previous version. A completed step is announced in the footer's status region ("Save: done."); the focus returns to the step's button when the new version still draws it, else to the heading. `FooterDisabled` is a busy indicator, not authorization.

## Comment side column

[ADR 0010](../../../docs/adr/0010-comment-threads-per-audience.md); behaviour in [docs/features/notifications-and-comments.md](../../../docs/features/notifications-and-comments.md#comment-threads).

1. One side tab per audience (`CommentAudience`: Internal, Staff, Customer), each backed by its own `CommentContainer`, created with its first comment. The audience is the container, never a flag on a comment.
2. Threads render only through `CommentBubbleList`, drawn by the foundation: a body never places a thread or a side column of its own.
3. **Wiring.** The entity implements `ICommentedEntity` (always a state entity: its delete meets `CommentThreadsBlockDelete`). Its service declares its audiences with their permissions (`CommentThreadAccess(audience, readPermission, postPermission)`) and offers `Get{Entity}CommentsAsync(id, ct)` (`CommentService.GetThreadsAsync<TEntity>`) and `Add{Entity}CommentAsync(id, audience, text, ct)` (`CommentService.AddCommentAsync<TEntity>`). The context overrides `LoadCommentThreadsAsync` and `PostCommentAsync`, both or neither, each one call to its entity's service or to the child service behind one of its properties (`service.Conversations`), which hands on to `CommentService` exactly once (`DialogArchitectureScanTests`).
4. **Who sees what.** The server decides: only the threads whose read permission the reader holds, each with or without a composer by its post permission; no thread means no column. A customer portal never gets Internal.
5. **Loading.** Threads are read beside the entity on every load of a saved row; a new record has no thread. A refusal or error shows in the column, never as "could not open".
6. **Posting.** A comment saves at once through the thread service; it never goes through `OnBeforeTransition`, the updater or the footer, so a post leaves the edits unsaved and the footer's answer standing. A post notifies only through its thread's post effects. The column is inert while a step runs.
7. A transition's reason (decline, reject, cancel) comes through its comment prompt and lands in the entity's thread as a note naming its step, inside the transaction ([TRANSITION-ORCHESTRATION.md](TRANSITION-ORCHESTRATION.md#sequence), step 9).
8. **Attention.** A tab's badge turns to the warning tone when the thread needs the reader: its whose-turn answer where the entity keeps timestamps (`CommentThread.Turn`), else `CommentThread.AwaitsReply`. There is no per-user read table. An entity that keeps timestamps stamps them through the post's effects (`CommentPostEffects`: one `UPDATE` of its row as the post transaction's first statement).
9. **Drafts** are the context's (`DraftOf`, `KeepDraft`), in the circuit only, never browser storage, keyed by thread.
10. **Conversations tab.** A context whose entity's children hold the conversations (a job's assignments) overrides `LoadConversationsAsync` (null for a reader who gets no tab), `LoadConversationThreadAsync` and `PostConversationCommentAsync`, each one call to its service or child service, and names the tab (`ConversationsLabel`). It is read with every load, and again when a child dialog opened from one of its lists closes without reloading it (`RefreshConversationsAsync`).
11. **A thread named for its reader.** Where the audience's name does not fit the reader, the service sets the thread's `Title` and `Readers`. A thread whose comments cross to another tenant (the customer thread) passes effects with `Crosses` and queues its integration message in `After`, on the post's context.

## Dialogs without a lifecycle

Everything else (a confirmation, an error, a message, a prompt, a form of something without states) opens through `DialogServiceExtensions` (`ConfirmAsync`, `ShowErrorAsync`, `ShowMessageAsync`, `PromptAsync`, `OpenFormDialogAsync`) under `FormDialogHeader`, its form inside `FormDialogFrame` ([docs/features/lists-and-dialogs.md](../../../docs/features/lists-and-dialogs.md#dialogs)). Their host (`FormDialogHost`) owns focus and Esc. Never use one for a state entity: `DialogUsageScanTests` refuses a state-entity body opened through `OpenFormDialogAsync`, and its allow-list holds the extensions' own two hosts alone. A row of a child list that is no state entity (a user's role holding) opens a form dialog of its own, whose opener answers the child list a `StateEntityDialogResult`.

## Exceptions

A bulk dialog may put a `TransitionButton` per row (assigning many staff members to work patterns at once); each button still checks its own transition. Login-driven transitions run without a button.
